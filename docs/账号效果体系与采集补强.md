## 1. 一段话结论

**账号榜要做，但不能按三份方案里任何一份的原定义上线**：现有 PostMetric 只在计数变化时写行（`backend/app/services/metrics.py:62-77`）、日闸门失败不回退（`AgentForegroundService.kt:176,182`）、任务表 30 天被清空（`config.py:29` + `tasks.py:49`）、账号归属从未落库（`entities.py:263`，实测 0 行有值），导致**「没涨」「没采到」「采了但没上报成功」「历史已被清理」四种完全不同的状态在数据库里长得一模一样**——直接做榜等于把回采链路的健康度当成内容表现展示给运营。因此本方案把顺序倒过来：**先补可观测性（新增 `CollectionRun` 回采运行记录）与归属冻结（`account_key` 写入时定死 + 软删除），再定增量口径（中国自然日 + as-of 基线 + 日均归一 + 三类"不可排名"显式标记），最后才做账号榜与首屏产能区**；采集侧只做两件确定有收益的事——**修可靠性（分批上报、闸门分离、平台轮转、回采移出 ticker 线程）和补语义（`published_at`、grid/detail 来源标记）**，不做 OCR、抖音不逐篇点进详情页（在真机取证证实列表文本被截断之前），小红书继续点进详情但改为分层且必须先带来源标记。全程 33 人天，分 6 期，P0/P1 不产出任何新界面但决定后面所有数字是否可信。

### 2.4 明确回答两个问题

#### 【要不要 OCR】—— **不要。**

1. **要的数字全部已经是可访问性文本**：抖音四项是 `text` 节点、小红书四项是 `contentDescription`，两套解析器都在线上跑通。用 OCR 替换一个确定可靠的来源，是拿准确率换不确定性。
2. **OCR 唯一能多拿的是大字报封面上烧进图片的文案**。我们自己的帖，封面文案本来就在 `ContentItem.cover_title`；外部帖的封面文案与正文高度重合，而二创引擎吃的是正文结构不是封面像素。
3. **成本是重新引入刚砍掉的东西**：需要 MediaProjection 截图 + 端上 OCR（ML Kit ≈ +10MB APK）或把图片回传（现链路只走 JSON），并且要**逐篇导航到详情页截图**——正是下面判定为不值的成本，还要再乘一遍。
4. **真正需要 OCR 的两个场景都不在范围内**：采他人/竞品作品（feed 里文案不暴露给可访问性，现有覆盖度为 0）、页面退化成 Canvas 渲染（尚未发生）。

**复活条件（写进文档，不是计划）：** 当且仅当 D4 的 adb 取证证实作品分析列表被应用层截断，**且** `readFirstComment` 也拿不到完整正文时，才把「图文详情页截图 + OCR」作为兜底重新评估。

#### 【要不要点进详情页】—— **抖音不点；小红书继续点，但改分层，且分层的前置条件是先做来源标记。**

**抖音：不点。** 抖音在作品分析列表上一次性拿到全部四项指标 + 发布时间，点进详情页只可能多拿"完整正文"，而这个收益完全取决于 D4 取证结论；点进去的代价是每篇约 4 秒、乘以 40 篇 = 160 秒，全程阻塞心跳。**先取证，后决策。**

**小红书：必须点，但不能对全量点。** 判断依据只有一条——**这次导航买到的东西是否进入第一指标**：

- **收藏 + 评论**：网格层拿不到，而它们是互动的两个加数。**每一篇都需要**，否则小红书的互动等于"只算赞"。
- **正文**：只喂 remix，而 `EXEMPLAR_LIMIT = 10`（`content_engine.py:173`）。**只有头部十几篇需要。**

两者同页取得，所以省不了"分开取"，只能省"取的篇数"。分层规则：

- **A 层（每次全量）**：网格扫描所有笔记，修 X1 的「万」正则。
- **B 层（开详情）**只对满足任一条件的笔记开：① 本地从未见过；② 网格赞数较上次有变化；③ 服务端还没有它的 body。**单轮上限 12 篇 + 整轮墙钟预算 90 秒**，按网格赞数降序取。判据存 Agent 本地 `SharedPreferences`（`title → lastLikes/seenCount`），不加协议字段。

> **⚠ 分层的阻塞前置条件（不满足就不许上线分层）：** 现在合并规则是"详情值 > 0 时优先，否则回退网格值"（`AgentForegroundService.kt:431-442`），而网格给的是**阅读**、详情给的是**浏览**，本来就是两个数。一旦"这轮不开详情"变成常态，同一篇的 views 会在两种口径间来回摆动；收藏/评论在不开详情的轮次直接落 0（`:446`），而 `record_metrics` 只要四项有任何变化就插新快照，时间线会变成锯齿，as-of 差分会算出大额负增量再算出等额正增量。**必须先做 2.5 的 `source` + `null` 语义，分层才能上。**

### 2.5 上报协议改造（这一节是采集侧收益最大的部分）

当前协议：`POST /agent/metrics`，`{device_id, platform, posts:[{title, body, views, likes, collects, comments}]}`（`AgentApiClient.kt:81-105`），DTO `dto.py:251-264`。

**四处改造：**

**① 字段扩展（`dto.py:248-264`）**

```python
class PostMetricItem(BaseModel):
    title: str = ""          # ← 改：field_validator 截断到 200，不再 max_length 硬校验
    body: str = ""           # ← 改：field_validator 截断到 3000
    body_source: str = "list"        # 新增: list | detail | comment
    metric_source: str = "detail"    # 新增: grid | detail —— 小红书分层的口径标记
    published_at: str | None = None  # 新增: 平台页面上读到的原始字符串
    views: int | None = 0            # ← 改为可空
    likes: int | None = 0
    collects: int | None = None      # 新增可空语义: null = 本轮未观测（不是 0）
    comments: int | None = None
    shares: int = 0

class MetricReport(BaseModel):
    device_id: int
    platform: str = "douyin"
    account_id: str | None = None    # 新增: Agent 当场从页面读到的平台号
    round_id: str                    # 新增: 本轮回采的 UUID
    batch_index: int = 0             # 新增
    batch_total: int = 1             # 新增
    expected_total: int = 0          # 新增: 本轮预计上报总条数
    status: str = "ok"               # 新增: ok | failed | partial
    error: str | None = None
    posts: list[PostMetricItem] = Field(default_factory=list, max_length=100)  # 50→100
```

**为什么 `max_length` 必须改成 `field_validator` 截断：** 现在是 Pydantic 校验不是截断，一条超 200 字的作品会让**整批 422**，Agent 端只落一行本地文案（`AgentForegroundService.kt:366-367`），而日闸门已提前置位 → 当天整台设备的数据全丢。这是整个方案里性价比最高的一处改动。

**② 分批上报 + 轮次信封。** Agent 每批 40 条逐批 POST（`AgentForegroundService.kt:360` + `AgentApiClient.kt:81-105`）。后端只有在 `batch_index` 全部到齐时才把该 run 标成 `complete`；不完整的 run 在 quality 块里单列 `partial_rounds`，**且不作为 as-of 基线的合法观测点**。Agent 对失败批次在本轮内重试 2 次再放弃。

**③ 失败也要上报。** 导航失败、树读空、到不了作品分析页（`AgentForegroundService.kt:508`）时，POST 一条 `status=failed, posts=[]` 的空报告。**这是让后端第一次能看见"这台今天没采成"的唯一办法。**

**④ 日闸门拆分 + 平台轮转。**

- `AgentPreferences.kt:52,56` 拆成 `lastXhsMetricsAttemptAt / lastXhsMetricsSuccessAt`（抖音同理）；开跑前只写 attempt，只有 `reportMetrics` 返回成功才推进 success。
- 失败退避：30min → 2h → 6h，每平台每天最多 3 次尝试。
- **`AgentForegroundService.kt:170-184` 的 else-if 必须改成轮转**（上轮跑了 XHS 这轮先看抖音）。否则一台 XHS 持续失败的设备会每 30 分钟抢占 idle 分支，把抖音永远挤到后面——而 22 个抖音号是当前数据的主来源。

**⑤ 回采移出 ticker 线程。** 现在整段跑在 4 秒 ticker 的单线程上、`networkBusy` 全程 true（`kt:32,84,213-215`），抖音已约 60 秒、方案要提到 70/90 秒，而 `device_offline_seconds = 45`（`config.py:22`）。后果是**每轮回采都会触发掉线 critical 告警**，运营会去点"检测设备"甚至刷机（刷机丢登录态 → 榜单更空）。改法：回采另起线程（群发已有先例 `kt:540`），心跳与领任务不受阻；同时 Agent 开跑前发一次带 `busy_until` 的心跳，后端对 busy 设备把掉线阈值放宽到 `busy_until + 30s` 并抑制该窗口的掉线告警。

## 3. 数据体系

### 3.1 时间口径：一律中国自然日

产品里所有"日"语义都是中国自然日（`tasks.py:33 _CN_TZ`、`:84 cn_day_start_utc`、`:394 _cn_day_bounds_utc`），而 `captured_at` 存的是去掉 tzinfo 的 UTC。**统计侧必须复用同一套函数**，否则 sparkline 的最后一格和首屏"今日已发"不是同一天，UTC 16:00 之后的回采会掉进前一天的桶。

- `resolve_window(window, from_, to)` 复用 `_cn_day_bounds_utc`：近 7 天 = `[cn_day_start(now - 6d), T1)`
- 日分桶一律 `date(captured_at, '+8 hours')`
- API 响应的 `window` 块显式带 `"tz": "Asia/Shanghai"`

### 3.2 序列身份：`post_key` 的唯一定义

三份方案给了三个互相冲突的定义（带 device_id / 不带 / 直接用三元组），混着实施会把同一篇拆成两条线。**统一为：**

```python
post_key = sha1(f"{platform}|{account_key}|{_norm(title)[:24]}").hexdigest()[:16]
```

- **与 device 彻底解耦**：云机重刷/换机是这套矩阵的常规操作，带 device_id 会让每次换机都把序列劈断、第一次回采被误判为"新发"。
- `_latest_metric`（`metrics.py:34-46`）的回查键从 `device_id + title` 改为 `account_key + post_key`。
- `_norm`：去空白/标点/emoji/`#话题`，NFKC 归一。
- **这个定义只允许在 `metrics_core.py` 里出现一处**，验收里加 grep 断言。

> **已知残留风险（不修，只标注）：** 身份仍是标题哈希。二创引擎改正文、平台换截断方式、两篇作品前 24 字相同，都会让序列裂开或合并。根治要等平台真作品 ID（抖音 item_id / 小红书 note_id），现链路完全没有。裂开的表现是"新发作品"，所以展开行必须标注"按标题去重"。

### 3.3 「近 7 天互动增量」的精确定义

#### 3.3.1 基础量

```
认同(approval) = likes + collects
互动(engagement) = likes + collects + comments
播放(views)  —— 并列展示，同算法算 views_delta，不参与排序
shares —— 恒 0（Agent 不上报，AgentApiClient.kt:86-96），不入公式、不展示
```

> **⚠ 口径警告（必须写进 UI）：** 实测抖音侧互动中 **71.4% 是评论**（likes 7158 / collects 800 / comments 19838），小红书 36.9%。榜首清一色是买房焦虑、婚前加名字这类争议帖。**按总互动排名 ≈ 按吵架量排名**。本方案的处理：主排序保留用户已定的"互动"（尊重决策），但**行内强制拆成「认同 / 评论」两段占比条**，并提供一个"排除评论"的排序切换；列头常驻一行小字「评论含争议流量，不代表认同」。见第 9 节待拍板 #1。

#### 3.3.2 取值规则：as-of / LOCF

窗口 `[T0, T1]`：

- **T1 不取 now**，取**该账号最近一次 `status=complete` 的回采批次时刻**（防止"点一次更新数据就全站涨"的零成本指标操纵）。
- **T0** = `cn_day_start(T1 - 6d)`。
- **end** = `captured_at <= T1` 的最后一个快照。
- **baseline** = `captured_at < T0` 的最后一个快照（**窗口起点之前最后一次观测**，不是窗口内第一个）。
- `delta = engagement(end) - engagement(baseline)`。

**为什么必须是 as-of 而不是"窗口内第一行"：** `metrics.py:62-77` 决定了"四项计数完全不变就不写行"，一个作品在 7 天里可能有 0 行、1 行或多行（实测 234 个序列里 94 个只有 1 行）。取窗口内第一行做基线，等于每个采集间隙都丢掉一段增长，且**不可加**——把一年切成 52 个周窗口求和会远小于生命周期真实增长，对账立刻失败。as-of 满足望远镜性，是"账号榜 = Σ作品 delta = 内容榜同窗口 delta"这条恒等式成立的前提。

**同理不用 `max - min`**：计数会真的下降（评论被删、取赞，实测相邻快照互动下降 10 次），更常见的是读数为 0 的解析故障。规则：`end - baseline` 带符号，**不做非负裁剪**（裁剪破坏可加性）；账号聚合时拆成 `+X / -Y` 两个数分开展示，主排序用 `+X`；单序列跌幅 > 20% 且绝对值 > 50 时打 flag 进 quality 块。

#### 3.3.3 **排序键用日均，不用裸 delta**

实测相邻快照间隔 p50 = 0.17 天、p90 = 2.77 天、max = 4.76 天。as-of 让"7 天"实际是 7~12 天的浮动窗口，**基线越陈旧、吃进的窗口外增长越多、delta 越大**——也就是说**回采越不稳定的号排名越高**，偏差幅度远大于账号间真实差异。

```
observed_days = (end_at - baseline_at) / 86400
eng_delta_per_day = eng_delta / observed_days     ← 主排序键
eng_delta                                          ← 只用于展示与对账恒等式
```

`observed_days` 偏离窗口长度超过 ±25% 的行标灰，tooltip 给出真实区间。**一个数不能同时服务排名和对账，必须拆成两个字段。**

#### 3.3.4 三类「不可排名」必须显式，不能装成 0

| 类别 | 判定 | 处理 |
|---|---|---|
| **无基线序列** | 该 `post_key` 在 `T0` 之前没有任何快照，且**不是**窗口内新发（无 `published_at` 佐证） | 既不计 0 也不计绝对值，单列「待观测 N 篇」。**排序只使用有真实基线的序列子集**，行上返回 `ranked_posts / total_posts`；当占比 < 0.5 时该行不渲染任何名次与主数字，只显示「数据不足以排名」 |
| **窗口内新发** | `published_at >= T0`（±24h 缓冲，见 8.3 时钟风险） | `baseline = 0`，绝对值计入 delta，但**必须单独返回 `delta_from_new` / `delta_from_existing` / `posts_new`**，UI 用浅色分段条把"新发拉动"与"老帖增长"并列。运营看到一个号冲上第一时必须能判断是内容好还是发得多 |
| **冷启动账号** | 该 `account_key` 的观测次数 < 2 | `status = cold_start`，**不参与排序、沉底**，绝对值照常展示，计入 `quality.accounts_cold_start`。（**判定用"观测次数 < 2"而不是"最早快照 vs T0"**——后者取决于几小时的采集先后，不取决于任何业务事实） |

**外加一条前置门（产能优先）：** 任何一行 `posts_published_in_window == 0` 时，主指标位置**不显示分数与名次**，直接显示「本周未发布」+ 一键跳该设备的登录/健康/自动发布开关。实测 `deviceaccount` 27 行里 `auto_publish` 全为 0、`logged_in` 7 个 NULL / 11 个 0 —— 停更号被读成"低效号"会导致运营去改选题而不是去登号。**产能是效果的前置门，不能并列成两个可比的数字。**

#### 3.3.5 参考 SQL（SQLite 3.50.4 已验证支持窗口函数）

```sql
WITH end_row AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY account_key, post_key
                               ORDER BY captured_at DESC) rn
  FROM postmetric
  WHERE captured_at <= :t1 AND metric_source = 'detail'   -- 口径隔离，见 2.5
), base_row AS (
  SELECT account_key, post_key, views, likes, collects, comments,
         captured_at AS baseline_at,
         ROW_NUMBER() OVER (PARTITION BY account_key, post_key
                            ORDER BY captured_at DESC) rn
  FROM postmetric WHERE captured_at < :t0 AND metric_source = 'detail'
)
SELECT e.account_key, e.platform, e.source,
       SUM((e.likes+e.collects+e.comments) - COALESCE(b.likes+b.collects+b.comments,0)) AS eng_delta,
       SUM((e.likes+e.collects)            - COALESCE(b.likes+b.collects,0))            AS approval_delta,
       SUM(e.views - COALESCE(b.views,0))  AS views_delta,
       SUM(CASE WHEN b.post_key IS NULL THEN 0 ELSE 1 END) AS ranked_posts,
       COUNT(*) AS total_posts,
       MIN(b.baseline_at) AS oldest_baseline
FROM end_row e
LEFT JOIN (SELECT * FROM base_row WHERE rn=1) b
  ON b.account_key=e.account_key AND b.post_key=e.post_key
WHERE e.rn=1
GROUP BY e.account_key, e.platform, e.source;
```

### 3.5 归属：写入时冻结 + 软删除 + 可回滚

现状是三个坑叠加：`PostMetric.account_id` 从不写（实测 0 行）；`device_id`/`content_id` 无外键且 `pragma foreign_keys = 0`（`db/session.py:31-40`）；换号走 `accounts.py:26-31` 原地覆盖。结果 **638 行里 435 行（68%）指向已不存在的设备**。

**① 字段语义先纠正。** `PostMetric.account_id` 是 `str | None, max_length=64`（`entities.py:263`），语义是**平台账号号**（抖音号/小红书号），**不是 DeviceAccount 的行 id**。两份方案都写成 INT 是错的——SQLite 动态类型会静默接受，迁 Postgres 时直接崩。**保持 str 语义，另加 `device_account_id: int` 存行 id。**

**② 新增列（`entities.py:253-271`）：**

```python

    # {platform}:{DeviceAccount.account_id}；号未知 → {platform}:dev{device_code}
    # 设备已删的历史行 → orphan:{device_code}:{platform}
```

**③ `account_key` 以「上报时读到的号」为准，不是以数据库当前值为准。** `DeviceAccount` 只在收到 `/agent/accounts` 或运营点「更新账号」时才更新（`accounts.py:26-31`），而回采与账号上报没有先后保证。手机上已换号但 DeviceAccount 还停在旧号时，freeze-at-write 会把旧号永久写到新号的作品上。因此：上报体带 `account_id`；**后端发现上报值与 DeviceAccount 不一致时，拒收本轮并置 `account_refresh_requested=True`，下一轮再采**。

**④ 软删除。** `DeviceAccount` 加 `archived_at / archived_reason`（`switched|deleted|device_deleted`）；`devices.py:399-407 delete_device` 与 `:410-433 delete_account` 改置位不删行；`accounts.py:19-36 upsert_account` 检测到同 `(device_id, platform)` 上报不同 `account_id` → 归档旧行 + 新建行，**不再原地覆盖**。矩阵页照旧看不见归档行，账号榜的历史区能查到。

> **为什么软删是产品要求而不是技术洁癖：** 账号榜给的是同一批分发内容的推荐结果排名（实测 21 个 title 出现在 ≥2 台设备上）。配上现在的硬删 + 换号重置，**洗号是改善排名最便宜的手段**。软删从产品上保证"删除不能改善任何聚合数字"。

**⑤ `device.id` 复用风险。** `device` 表 DDL 是 `INTEGER PRIMARY KEY` **无 AUTOINCREMENT**，`delete_device` 真删行，新设备可能拿到同一个 rowid，把 435 行孤儿挂到不相干的新机上。**迁移里改成 AUTOINCREMENT，且孤儿伪账号用 `device_code` 命名而不是 `dev{id}`。**

**⑥ 可回滚。** 新增 `POST /analytics/rebind`（`require_admin_role`，带 `dry_run`、返回影响行数、写审计），归属错了必须能改回来。

### 3.6 自有 / 外部：冻结 + 继承 + **覆盖率门槛**

判定 `content_id is not null or task_id is not null → ours`，但**必须在写入时冻结**：`_match_task` 的匹配率随 30 天清理单调下降，查询时判会让同一篇作品今天算 ours、下个月算 external，增量口径直接崩。**继承规则：** 同一个 `(account_key, post_key)` 序列一旦曾被判为 `ours`，后续快照一律 carry forward。回填不到的历史行 → `unknown`，**单列一档，不塞进 external 里假装知道**。

**归属的根治不是 rematch，是新建一张不参与清理的轻表：**


`_finalize_content` 成功时写入，`_match_task` 改查它。`POST /analytics/rematch` **明确只承诺 `retention_days` 以内**，返回值区分「可恢复」与「任务已清理无法恢复」。

**删掉方案①的跨设备兜底。** 实测 21 个 title 出现在 ≥2 台设备上（同一篇分发到多个号是常态），承载 25.6% 的互动。用 `match_key` 跨设备相等去救孤儿，会把已删设备的快照挂到另一个在用账号上——外部变自有、内容榜重复计数、归属错乱，而且因为 source 冻结 + 继承，**错误永久固化**。孤儿归入伪账号即可。

> **🚩 上线顺序硬约束：** 实测 `content_id` 非空只占 13.2%、只承载 10.8% 的互动。一旦按方案打上「自有/外部」标签并显示占比条，首屏当天就会宣告「我们系统只贡献了 11%」——而这是采集缺陷不是贡献事实。
> **在 rematch + PublishedPost 上线并人工抽检误配为 0、关联覆盖率 ≥ 90% 之前，UI 只准显示「未关联 N 篇」的绝对数，绝对禁止显示百分比、占比条或饼图；首屏不做任何「我们的贡献」类文案。**

### 3.8 物化时机的量化阈值

**现在不物化。** 实测 638 行 / 234 个序列 / 1.4MB，离阈值差两个数量级。

增长模型 `rows/day ≈ A × P × C × r`：现状实测 ~30 行/天（~11k/年）；全量 44 账号 × 50 条 × r≈0.25 ≈ 550 行/天（~200k/年）；理论上限 2200 行/天。

**触发任一即物化：**

| # | 阈值 |
|---|---|
| 1 | `postmetric` 行数 > **200,000** |
| 2 | 窗口内活跃序列数 > **3,000**（44 账号 × 50 篇 = 2200，仍在阈值内） |
| 3 | 生产笔记本 `GET /analytics/accounts`（page_size=20）**p95 > 400ms** |
| 4 | 榜单查询占用读连接 > 5% wall time |

**现在只做两件事：** 加 3.7 的复合索引 + 账号榜响应 **60s 进程内 TTL 缓存**（后者更重要——前端轮询才是真正的放大器）。

**阈值触发后的形态（存日增量而非日累计，任意窗口退化成同一张表的 SUM）：** `PostMetricDaily(day, account_key, post_key, ..., eng_delta_1d, views_delta_1d, filled, first_seen)` + `AccountDailyRollup(day, account_key, platform, source, eng_delta_1d, ...)`；write-through **必须在 `record_metrics` 的同一个事务里**（SQLite 单写者，另开事务会跟回采抢 `busy_timeout=5s`）；每晚重算最近 8 天自愈；切换前逐行 diff 必须为空。

**留存策略（现在完全没有，必须补）：** 在 `main.py` 的 `_retention_loop` 里加一条 PostMetric 降采样——保留最近 90 天全部快照，更早的每个 `post_key` 每月只保留最后一条（**保住 as-of 基线不丢**），日粒度物化表保留 400 天。降采样必须在 as-of 基线取法之后实现。

### 3.10 对账（口径漂移变成可见缺陷）

**单一事实源：** 新建 `metrics_core.py`。今天 `likes + collects + comments` 在 `metrics.py:153` 和 `:187` 各写了一遍——这就是口径会漂的起点。**验收加 grep 断言：全仓只允许命中一处。**

**三条恒等式：**
1. **账号 = Σ作品**：账号榜某行 `eng_delta` ≡ 下钻页所有作品 delta 之和。
2. **自有子集 = 内容榜**：`Σ 各行 ours.eng_delta` ≡ 同窗口内容级效果榜 delta 之和。
   > **⚠ 这条现在按构造不成立，必须先修内容榜。** `content_performance` 只按 `content_id` 分组取 `max(captured_at)` 再 `latest.setdefault` 取其一（`metrics.py:110-127`），而一条 `platform='both'` 的内容会扇出到两个平台、产生两条快照——内容榜只保留其一，另一个平台的互动被静默丢弃。**内容榜改为按 `(content_id, platform)` 分组、行上带 platform**（前端本就分两块榜，不改交互），对账改为按 `(content_id, platform)` 逐行比对。**这一步必须先于账号榜上线**，否则 reconcile 一上来就是红条。
3. **图 = 数**：`sum(series[].eng) ≡ eng_delta`。
   > 可加性只对「两个窗口都存在基线的序列子集」断言，并把该子集占比做成 `quality.additive_coverage` 摆在页面上。对全集只断言「差值可被逐项解释」。

`checks` 任一 `ok=false` → 账号榜顶部红条「口径校验未通过，数字暂不可信」。

**人工对账路径（三次点击，不需要 SQL）：** 账号榜行 → 展开下钻 → 顶部合计 = 榜单那行的数 → 某条带 `content_id` 的作品 → 跳内容级效果榜同一行 → delta 相等。写进帮助文案。

### 4.7 趋势图实现取舍

**画什么：不画 7 根日柱。** 实测 383 对相邻快照里 215 对（56%）间隔不到 12 小时（人工刷新连击，06-26 单设备一天有 7 个不同小时在写入），22 天里 9 天完全无数据。7 个日柱里注定有 2~6 个是空的，运营会把「周一那根柱子高」读成「周一发的内容好」——**那画的其实是"谁在什么时候点了更新数据"**。改为：**按真实观测事件排布的 N 个点，x 轴标观测时刻，空日不画**（既不画 0 也不画虚框）。观测点 < 3 时直接不画，显示 `5 次 / 7.9 天` 那一列即可。

**用什么画：自研内联 SVG**，一个约 35 行的 `<Spark points={{at,eng}[]} />` 组件。

理由：① 需求边界只有两个图形（76×22 行内 + 148px 展开），recharts/echarts 的 90% 能力用不上；② recharts +~500KB（含 d3 子包），当前 `dependencies` 只有 `lucide-react + react + react-dom`，零 UI 依赖是刻意的；③ **打包约束是决定性的**——`./build.sh` 产出两份前端（`dist` 桌面版 / `dist-web` 浏览器版），Tauri 离线运行、生产机 `192.168.1.100` 内网直连，CDN 方案不可用，任何新依赖要同时验证两条链路；④ 现有视觉语言（Oswald 大字 + 纸张底 + coral）是手写 CSS，图表库默认样式要大面积覆盖。

**逃生门（写进组件头注释）：** 当需求扩到「多账号叠加对比 + 缩放 + hover tooltip + 30 天」时，引 **uPlot**（~45KB，无依赖，Canvas），不要引 recharts，也不要现在预投。

**表格同理：自研薄 `<DataTable>`（约 150 行 TSX + 约 80 行 CSS），不引组件库。** 现有 `history-table`（`styles.css:2005-2017`）与 `token-table`（`styles.css:4852-4859`）已验证 grid 方案可用，问题是**第三次复制**——所以抽，但抽自己的。API：

## 5. 首屏产能区（优先级最高）

现有 `Overview` KPI strip 有三个真问题：

1. 「今日目标 = 各账号 `daily_quota` 之和」**口径错了**——用户已定 quota 是上限不是必发数，`43 / 58` 永远显示未达标，运营会对这个数字脱敏。
2. `runway = pending / (rows.length * 2)`（`Overview.tsx:164-166`）硬编码 2，且分母含离线/未登录号。
3. 完全没有「今天还有几个号没排期」——而这才是首屏唯一真正的行动点。

### 新首屏结构（自上而下）

**A1. 今日产能条**（一条水平 stacked bar，取代四个孤立数字）
四段：`已发成功 43` / `执行中 3` / `已排期待发 12` / `未排期空档 9 个号`。右侧文案：

> 今日已发 **43** · 执行中 3 · 待发 12 · **9 个账号今天还没排期**

「9 个账号今天还没排期」是可点主 CTA → 打开批量排期弹窗并**预选这 9 个**。这是首屏最高价值的一次点击。
**口径修正：分母 = 今日计划量（已排期任务数 + 已发数），不是 quota 之和；quota 只在排期时做上限校验（超限拦截并提示）。**

**A2. 产能 KPI 三格 + 异常一格**（复用 `.kpi-strip`）

| 格 | 数字 | 副文案 |
|---|---|---|
| 可发账号 | `21` | `共 27 个号 · 6 个离线/未登录`（可点 → 筛出这 6 个） |
| 今日进度 | `43 / 58` | 内嵌 2px 进度条；`计划 58 篇（上限 62）` |
| 内容库续航 | `6 天` | `按近 7 天日均 9.6 篇算`；<3 天 amber，<1 天 coral + 「去 AI 创作」按钮 |
| 异常账号 | `2` | 仅 >0 时着色；放最末格 |

**A3. 近 7 天产能小图**（A2 右侧，复用 `<Spark>`）：7 根柱 = 每天**实发篇数**（来自 `PublishedPost`，中国自然日分桶），一条虚线 = 计划线。
> 注意：这里用日柱是**正确的**——发布是我们自己触发的事件，每天都有确定值，不存在观测稀疏问题。回采指标才不能用日柱。

**A4.「需要处理 · 5」**（B 异常从"四格之一"降级为一个可收起清单）
每条一行 + 直达操作：
- `2 个账号限流/违规，已暂停发布` → 恢复正常
- `1 台在线但无障碍未就绪` → 查看处理说明

- `1 台离线超过 24 小时` → 检测设备

## 8. 风险与对策

### 8.1 数据正确性（blocker 级）

| 风险 | 对策 |
|---|---|
| **「0」与「未知」在数据层不可分**（`metrics.py:62-77` 计数不变不写行 + 日闸门失败不回退） | P0 建 `CollectionRun`，所有陈旧/`—`/quality 一律读它，绝不从 PostMetric 反推。这是整个方案的地基，不做则后面全部作废 |
| **as-of 让"7 天"实际是 7~12 天，系统性奖励回采最差的账号**（实测间隔 p90=2.77 天） | 主排序键改 `eng_delta / observed_days`；`observed_days` 偏离 ±25% 标灰并给真实区间；裸 delta 只用于展示与对账 |
| **窗口内无基线的序列占绝对多数**（实测 8 个账号里 7 个一条基线都没有） | 排序只用有基线的子集；`ranked_posts/total_posts < 0.5` 的行不渲染名次与主数字，显示「数据不足以排名」 |
| **「更新数据」是零成本的指标操纵杠杆**（只推 end 不推 baseline） | `T1` 取上一次 `complete` run 时刻而非 now；`refresh-metrics` 加 2h 最短间隔 + 记录触发人并暴露在 quality 块 |
| **时区错位**（`captured_at` 是 UTC，产品所有"日"是中国自然日 `tasks.py:33/84/394`） | `resolve_window` 复用 `_cn_day_bounds_utc`；日分桶 `date(captured_at,'+8 hours')`；响应带 `tz` |
| **小红书分层让 views 在 阅读↔浏览 两口径间震荡、收藏/评论落 0 制造锯齿** | A8 先做（`metric_source` + null 语义），差分只在同一 source 段内做。**A8 未完成不许上 A7** |
| **可加性硬验收在真实数据上必然失败**（新发注入 baseline=0、掉数、零值读三者任一都破坏 telescoping） | 只对「两窗口都有基线的子集」断言，把占比做成 `quality.additive_coverage` 摆在页面上；对全集只断言"差值可被逐项解释" |
| **序列身份仍是标题哈希**（二创改正文 / 平台换截断 / 前 24 字相同） | 无法根治（无平台 item_id）。缓解：展开行标注「按标题去重」；`ranked_posts` 暴露裂开痕迹；中期争取平台 ID |
| **published_at 时区与时钟不可信**（无时区字符串 + 云机未校时） | 上报带设备时区偏移与当前时钟，存原始字符串 + 归一化 UTC 两列；跨 T0 的判定加 ±24h 缓冲，不做精确边界比较 |

## 9. 需要拍板的问题（5 条）

**① 主指标是否继续把「评论」计入互动？**
背景：实测抖音互动 71.4% 是评论，榜首清一色争议帖；小红书 36.9%。按总互动排名 ≈ 按吵架量排名，且与真实业务目标（群发进群）零关联。
**推荐：** 短期**保留总互动作为主排序**（尊重已定口径），但强制行内拆「认同(赞+藏) / 评论」两段条 + 提供"按认同排序"切换 + 列头口径提示；**中期把 `group_message` 的进群数接进 PostMetric 或单独一张表，主指标换成"每篇带来的进群数"，互动降为诊断指标**。请确认是否接受这个中期方向并排进下一季度。

**② 排序键用「日均增量」还是「裸 7 天增量」？**
背景：as-of 让有效窗口在 7~12 天浮动，裸值系统性奖励回采最差的账号。
**推荐：排序用 `eng_delta / observed_days`，裸 delta 只展示。** 代价是运营看到的主数字是"+486/天"而不是"+3,820"，需要一次口径说明。

**③ 平台是否提供「全部」这个选项？**
背景：抖音播放量级、评论占比都与小红书差一个数量级，默认「全部」时抖音号必然霸榜、资源被系统性抽走。
**推荐：不提供「全部」，进页面必须选一个平台，默认抖音**（22 个抖音号 vs 7 个 XHS 号）。唯一允许的跨平台合并视图是各平台内百分位排名。

**④ 「自有 / 外部」什么时候允许对外露出？**
背景：现在 `content_id` 非空只占 13.2%、只承载 10.8% 互动，一旦露出占比就是「我们只贡献 11%」。真因是任务表 30 天被清 + 50 条回看窗口。
**推荐：设一条硬门槛——`PublishedPost` 上线 + rematch 人工抽检误配为 0 + 关联覆盖率 ≥ 90%，三条全满足前，UI 只显示「未关联 N 篇」绝对数，禁止任何百分比/占比条/饼图；首屏不做「我们的贡献」类文案。**

**⑤ 账号榜首版是否出全站名次？**
背景：矩阵把同一篇内容分发到多个号（21 个 title 跨设备，占 25.6% 互动），每号每天 ≤2 篇、7 天样本量个位数，账号间差异主成分是平台推荐波动；配上硬删/换号，洗号是改善排名最便宜的手段。
**推荐：首版出名次，但加三重闸门**（`rankable && ranked_posts ≥ 5 && posts_published_in_window > 0`，不满足显示「样本不足」），**同时在展开行提供「同一内容跨账号配对对比」**——后者才是真正剥离内容质量、看出账号运营差异的视图。若产品侧认为名次风险不可接受，可改为首版只出「自身环比 + 配对对比」，名次留到拿到进群转化口径后再上（该选项会减少 P3 约 1 人天）。

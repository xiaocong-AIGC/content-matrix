### 第 4 条的重算（用生产真实数据，不是方案里的外推值）

深圳 5 个号全部开着自动发布，`daily_target=3` → **15 篇/天**（9/8 起实测确认，之前是 5 篇/天）。

两个实测参数：

- **块内标准差 σ_within = 0.510**（log10(1+评论)，扣掉账号和周的固定效应，345 条残差 / 63 个块）
  —— 比方案假设的 0.551 小，也远小于批评者用 dev 库外推的 0.857
- **有效样本率 87%**（发出去且能拿到可归因回采读数的比例）

| | 每臂 | 检出 +30% | 检出 +50% | 检出翻倍 |
|---|---|---|---|---|
| 14 天 | 91 条 | 33% ❌ | 65% ⚠️ | 98% |
| **21 天** | **137 条** | 46% ❌ | **82%** ✅ | 99.8% |
| 42 天 | 275 条 | 75% | 98% | 100% |

**21 天成立，14 天不成立。** 14 天只够检出「翻倍」，而翻倍级的提示词改动基本不存在；
65% 的功效意味着真有 +50% 的改进也有三分之一概率看不出来 —— 那不是「没效果」，
是「不知道」，是最坏的结果。

### ⚠ 实验只在深圳跑 —— 这一条同时解掉了最大的障碍

复核第 1 条说「71% 的发布是人工排期，A/B 前提不成立」。但按城市拆开看：

```
9/8 起的 56 条图文任务
  深圳  54 条　人工排期 0（0%）　引擎自动 54（100%）
  北京   2 条　人工排期 2（100%）
```

**深圳 100% 由引擎选内容，人工排期一条都没有** —— 而全矩阵仅有的 5 个自动发布账号

代价是结论的外推范围只到这 5 个号；其它城市要么先开自动发布，要么等这一轮结论。

# 定稿：内容生成—优化—迭代闭环

## 一句话结论

走**「同号配对实验台 + 两层迭代」**：采集时刻搬到后端并钉死时段，内容与提示词各自有可追溯的身份，效果比较**只在同一个账号同一周内部配对做**，提示词的日常迭代靠**离线影子测试的确定性指标**（当天出结果），效果数据只用来做**每 6–7 周一次的主版更替**和**档位配额**。四个候选里它是唯一零致命的一版；其余三版的好东西我按下面第九节逐条嫁接进来了。

**不交付的两件事，现在就说清**：① 「模型按内容类型自动优化提示词并自动上线」本期不做，也不承诺时间点——数据支撑不了（见下）；② 多模态本期不做，输入不存在（见第五节）。

## 一、先清掉被证伪的前提

这一节比方案本身重要。下面每一条都在评审里被代码或数据推翻过，如果拿它们当理由买单，会买错东西。

**1. 「效果榜 400 条、浏览中位 11000、前 10% 门槛 40000」是错的。**
`content_performance` 是先按 engagement 排序**再**截断（`backend/app/services/metrics.py:157-158`），所以带 `limit` 拿到的永远是高分子集。全量真分布：中位 **4886**、p90 **16000**、p99 96770。所有阈值按真分布重定。接口要加一个不排序的取全口径，否则任何统计脚本永远拿偏样本。

**2. 「924 条样本」很可能是 924 **行**快照，不是 924 个帖子——这一条会决定「三档」成不成立。**
`PostMetric` 是变化事件流（`metrics.py:59-84`，四个计数全等就不写行）。本机 dev 库实测 638 行 = **234 个帖子，2.73 行/帖**，单帖最多 21 行，同帖内 log10(views) 的 **ICC ≈ 0.96**。三档表的 171+645+78 = 894 与「按行」完全吻合。若确实按行统计，设计效应 1.9–2.7，有效 n 从 894 掉到 ~350：A 档位次 CI 半宽从 ±0.0405 变 ±0.065，A vs B 的 0.081 差距对应 z 从 3.4 掉到 ~2.2，**Kruskal p 从 1e-3 级掉到 3e-2 级**。
→ 所有既有统计结论必须**按 note 级重算一遍**才能用（P1）。在重算完成之前，「三档」是待验证的假设，不是定论。我已经写死了退路：重算后 A vs B 的位次差 CI 若含 0，就退回**两档**（折半复现里只有两端稳定：「二选一」永远第 1、「清单攻略」永远第 8，中间 6 类在洗牌）。

**3. 「账号解释 17.2%，是内容类型 2.3% 的 7.5 倍」——方向对，倍数不能这么说。**
自由度未校正：22 个账号 21 df、8 类 7 df，零假设下期望 R² 分别是 2.3% 和 0.76%。每 df 的信号是 **2.5 倍**，不是 7.5 倍。而且 dev 库上 device 对 log10(views) 的 R² 只有 3.5%（低于零期望 6.0%）。
**但架构决定不变**：即便按 3.5% 算，按账号分臂两臂均值差的标准误也有 0.072 log10 = 1.18x，与要检出的 1.5x 同量级。所以「必须块内配对、不能按账号切臂」这个唯一不可逆的架构决定在 3.5%–17.2% 全区间都成立。只是不要拿 7.5 倍去说服人。

**4. 「按内容类型分别优化提示词」，数据在数月内证明不了。这是用户第 4 条的核心，所以放第一段。**
算术：档间效果差只有 **0.068–0.081 位次**。一次提示词改动要在效果数据上被看见，它的效应必须**大于整个类型效应本身**。按档做 A/B：A 档占产出 18.5% ≈ 2.5 条/天，分两臂后需 189 条/臂 = **151 天**；就算把 A 档配额抬到全量一半，也要 **56 天**。
→ 结论：**档段提示词只能靠离线过程指标 + 人的判断来调，不能靠效果 A/B。**效果数据只回答两个更粗的问题：全局主版该不该换（6–7 周一轮）、各档配额该不该动（集群随机，2–4 周交叉）。这句话必须写进流程文档，否则运营每改一次档段文案都以为有数据背书。

**5. 「发布时段就是 10-11 / 14-15 / 17-18」不是代码事实。**
`publish_windows()` 读 `AppSetting["publish:windows"]`，默认空串，而 `_due_by_plan` 在 slots 为空时**直接 return True**（注释：空 = 不限制，手机空了就发）。dev 库里没有这个 key。`schedule_windows.py` 的 `DEFAULT_WINDOWS = "10:00-11:00,14:00-15:00"` 是群发用的默认，不是发布。
→ **排 P2 之前必须去生产查这一个 key。**采集时段的整套论证挂在它上面。

**6. 「回采会再一次阻塞心跳、20 台误判掉线」不会重演。**
回采本来就跑在独立 `Thread`（`AgentForegroundService.kt:1098`），心跳不受影响；历史那次的成因（同线程阻塞）已修。真正的风险是**抢屏幕**（`:186` 的 `api.claim` 无条件执行，`metricsBusy` 只拦回采撞回采）和**PC 编排器并发**（每设备一个 watcher 线程，37 台同时 `am start`）。要防的是这两件，不是心跳。

**7. 「覆盖率告警 = scope 内应采条数 vs 实收条数」这个告警按原设计永远不会响。**
实收是手机从屏幕上刮到的**全部**笔记（20–30 条，多数是历史作品），应采是 scope 内我们发了几条（约 2 条）。`reported ≥ expected` 恒成立。要做到「昨天那 N 条各拿到一个点」必须逐条对齐，而对齐靠 `_match_task` 的**前 12 字模糊匹配 + limit(50)**，匹配率 13%（84/638，小红书 13/321 = 4%）。
→ 覆盖率告警必须排在**匹配改严之后**。这支团队有「看到告警就去刷机、刷机丢登录态」的前科，一个默认高误报的每日告警比没有告警更贵。

**8. 「PostMetric.account_id 表里有」——有列无数据，0/638。**
`record_metrics` 从来不写它。主指标的分组键要靠 `(device_id, platform) → DeviceAccount` 反查，或先回填。「效果榜返回 account_id」如果照抄，交付的是一列空值。

**9. 「09:00 采集不撞车，因为日报也在 09:00、共用同一批空闲设备」——理由是错的。**
日报（`DIGEST_HOUR_CN = 9`）是服务端 webhook，一台手机都不碰。09:00 的两条真理由（避开发布窗、周报能读到新鲜数据）够用，这条删掉。

**10. `_dup_corpus` 只修一半会引爆内容池。**
两处 `limit(400)` 都没 `order_by`，SQLite 返回 rowid 升序 = **最老 400 条**（生产已发布 900+，等于查重看不见最近内容）。但查重命中写的 status 是 `duplicate` 而不是 `rejected`，而语料的过滤条件是 `status != "rejected"`。一旦加上 `order_by(id.desc())`，语料翻成最新 400 条，其中会混进影子测试稿——按每周真稿 94.5 + 影子 400 算，语料里绝大多数是永不发布的测试稿，而它们恰好和生成器下一批最像。`DUP_REJECT=0.90` 会开始把真草稿判重，症状是内容池水位下行 + 群里「内容告急」，看不到原因。**两处必须同期改，且影子稿用独立 status 隔离。**

**11. 「地名泄漏被硬闸挡着」可能是空转。**
`city_tokens()` 读 `AppSetting`，**代码里没有默认词表常量**（对比 `DEFAULT_MIN_DAYS` / `DEFAULT_BATCH_CAP` / `DEFAULT_QUALITY_FLOOR` 都有默认值）。dev 库 appsetting 里没有 `supply:city_tokens` 这个键 → `table = {}` → 整个地名闸跳过。这正是方案自己在批的假旋钮，只不过这次假在安全网上。

**12. 「参考样本的门槛 · 互动 ≥ 120」是假旋钮。**
`content_supply.exemplars_for` 全项目零调用，是死代码；它是 `quality_floor` 的唯一消费者。运营调了半年，一次没生效过。

**13. `draft.model` 和 `cost_cny` 在说谎。**
`content_engine.py` 用 `resolve_model(session)` 发起调用，却把 env 里的 `settings.deepseek_model` 写进库。生产 `AppSetting.deepseek_model = deepseek-v4-pro`（**推理模型**），库里 95 条草稿全标 `deepseek-v4-flash`。而这两列正是将来「哪版提示词更划算」的唯一依据。顺带：v4-pro 是推理模型，`deepseek.py` 专门为它写过「思考阶段被截断、正文为空」的报错，`max_tokens = min(32000, 6000+count*1500)` 目前够，但这条风险的实测数据我们没有。

**14. 「自动生成的草稿要人工采纳才进池」——错，只对 AI 创作页那条路成立。**
`content_supply.run_once` 过 `check_draft` 之后**直接建 `ContentItem(status=PENDING)`**，`_pick_content` 按 PENDING 取最老一条发布。也就是说每天一半以上的内容**没有人读过一个字**就发到真号上，而 `check_draft` 只查四件事：长度、外地地名（可能空转，见 11）、写死日期、封面撞库。没有一条读得懂「这段话写歪了」。这是必须在 P3 处理的，见第六节。

**15. 两个小的：** 「发过 25-30 天掉出效果榜」不准——purge 删 `PublishTask` 不删 `PostMetric`，行还在，症状是新快照匹配不上任务、`content_id` 变 null、**数字冻结**。`PostMetric.shares` 是死列（Agent 从不上报），界面撤掉。

**16. 数据出处必须先钉住。**
本机唯一有数据的库是 dev（638 行、234 帖、最后采集 2026-07-09、xhs 321 行全部来自一台人手驱动的机器）。「全库 924 条、douyin 922 / xhs 2」只能来自生产，且与 dev 的 xhs 321 直接冲突。仓库里没有任何分析脚本（`tools/` 下只有 provision / orchestrator / media_audit / resolve_css / stress_test），Kruskal、omega²、bootstrap 5000、Holm 都是仓库外一次性算的，谁都无法重跑。
→ **P0 的第一件事：把分析脚本提交进 `tools/`，标明库和口径，在生产上重跑一遍。在那之前本方案所有阈值都是待重算的。**

## 二、定期采集

用户两条要求逐条落，但触发权和时刻**全部搬到后端**，Agent 只保留「怎么采」。

### 谁触发

后端一个 `_metrics_collect_loop`，60 秒一轮，**每轮 `await asyncio.to_thread(...)`**。抄 `_notify_dispatch_loop` 或 `_content_supply_loop` 的形状——注意别抄 `_auto_broadcast_loop`，它恰恰是唯一没用 to_thread 的那个。新 loop 只做 SQLite 读写 + 置标志位，**零网络调用**，这是红线。

Agent 侧删掉 `METRICS_INTERVAL_MS` 和两个 `lastXxxMetricsAt` 闸门，只留 36 小时兜底（后端挂了不至于完全不采）。这一步顺手就修掉了那个**线上正在发生的确定性 bug**：两个平台是 else-if 共用同一个 `now`、闸门先扣后跑，小红书分支先命中并起线程，4 秒后抖音分支先写额度再进 `runMetricsOffTicker`，被 `compareAndSet` 直接顶回——**装了小红书的手机，抖音每天 0 条，手动点「更新数据」也救不回来**（因为按钮把两个闸门同时清零，顺序不变）。

### 时刻（这是拍板项 1）

| | 窗口 | scope |
|---|---|---|
| 每日 | **09:00–09:50**（推荐值） | 昨天 00:00–24:00 北京时间发布的 |
| 周五 | **08:00–09:20**，且**周五只跑周采，不跑日采** | 上周五 00:00 – 本周四 24:00 发布的 |

两个 `AppSetting` 键，沿用现成的 `parse_windows` / `plan_times`。周报保持周五 09:30，天然读到当天刚采完的数据，不用动 `notify_sweep` 的常量。

**为什么建议 09:00 而不是用户原话的 10-11**，三条都可验证：
- 10-11 很可能就是第一个发布窗（**前提是生产上 `publish:windows` 真的设了，先查**）。而设备上采集与发布**零互斥**，后端也拦不住（采集期间心跳报 `currentTask=null` → 设备被置 ONLINE → `claim_next_task` 全程没有「这台在忙别的」判断）。今天这是随机竞态，钉到 10-11 就变成**每天必然**。
- 数据成熟度打平。昨天最晚 18:00 发的，今天 09:00 采年龄 15h、10:00 采 16h。对一个类内 1 个标准差 = 8 倍的分布，1 小时不可分辨。
- 周报能读到当周最后一次采集。排 10-11 则周报永远差最后一天。

**如果坚持 10-11**，代价三件，都要一起做：① 采集时刻必须和发布时刻同源计算（同一个 `plan_times` 种子），派发前硬性避开该设备自己的发布时刻 ±8 分钟；② claim 双保险（Agent 端在 claim 前既判 `metricsBusy` **也判「有没有待执行的采集命令」**——只判前者抢不到那一拍，tick 里 claim 在采集分支之前）；③ 周报挪到 11:30。

### 37 台怎么排

单机占机实测拆解：抖音典型 34s（6s 启动 + 导航 12.9s + 8×1500ms 翻屏 + 2.6s 收尾），最坏 258s（导航 while 36 步全走「编辑主页」分支，然后返回空、白占机）；小红书 90–130s。

- 预算 180s/台（日采）、300s/台（周采）；**硬 wall-clock 上限 240s / 360s**（今天回采线程没有任何超时兜底）。
- **并发 cap = 4**。理由和发布侧的 `max_concurrent_publishes = 3` 同源（单 PC 编排器，每设备一个 watcher 线程）。日采 37/4 = 10 波 × 180s = 30 分钟，50 分钟窗口有余量；全部走最坏路径 10 × 258 = 43 分钟，仍装得下。周采 10 × 300 = 50 分钟，80 分钟窗口 OK。
- 派发时刻用 `plan_times(key=f"metrics:{device_id}")`，种子含设备 id + 日期，37 台自动错峰且「算一遍和算一百遍结果相同」，进程重启不重排。
- 派发前跳过：有 ACTIVE 任务的、下一个发布时刻在 8 分钟内的、心跳超 45s 的、今天该 kind 已有成功 MetricsRun 的。
- **「更新数据」按钮改走同一个队列**。今天它是一次性给所有在线设备打标，15 秒内 37 台全开采，完全绕过并发闸——而这正是运营刷完一批机后习惯按的按钮。

### 并发计数和卡死回收（这是原方案最大的漏）

- `MetricsRun` 唯一键 `(device_id, day_key, kind)`，幂等靠表不靠内存。
- **必须有 lease 回收器**：`dispatched_at + 480s` 过期即回收，照 `reclaim_expired_tasks` 的形状。否则一台手机采到一半重启，这条 run 永远不 finish，cap 名额永久泄漏，攒够 4 次全队静默停止。抖音导航失败走 252s 后 `return emptyList()`，而 Agent **只在 posts 非空时才上报**——空结果一个字都不发。这条不补，P2 上线一周内就会踩。
- 并发计数用「dispatched 且未 finished 且 lease 未过期」，把已派未领的也算进去，否则 15 秒心跳窗口内会超派。

### 失败谁知道

今天完全静默：`catch { updateLocalStatus("回采失败：…") }`，而 `updateLocalStatus` 只写 SharedPreferences + 通知栏，**不发任何网络请求**；`alerts.py` 里搜不到 metrics。唯一线索是周报里那句「N 个号整周没拿到数据」，依据 `max(captured_at)`，一周一次、藏在报告里、还会把「采到了但没涨」误报成「没采到」。

改法：MetricsRun 由后端派发时创建，Agent 上报带 run_id，成功写 finished + reported，失败上报 error。三档告警：单台失败只记录；同平台当天失败 ≥5 台 → **进企微群**；覆盖率不足 → 进群 + 排 19:30 补采（补的读数标记 backfill，不进判据）。闸门改成成功后才写，失败当天可退避 15 分钟重试 2 次。

### 顺手必修

- **上报分批**（每批 40）。`dto.py` 的 `max_length=50` + Agent 不分批 = 超了整批 422 静默丢，而**发得最多、最该被分析的号先出事**。周采覆盖 7 天必然逼近这个上限。
- **`published_at`**。抖音的正则已经匹配到发布时间，只是构造 `PostMetricInfo` 时没带上；加进 DTO 和表。小红书 grid 无日期 → 留空，靠 `content_id` join `ContentItem.published_at` 兜底。同时存 `age_hours`。
- **两处 `return@repeat` 是 continue 不是 break**（抖音 `stale>=2`、小红书 onMain）。不致命，但占机上界必须可算。
- **匹配改严**：`_match_task` 从「前 12 字模糊 + 先命中先返回」改成「优先精确/最长匹配 + 要求唯一命中，多命中就置 `content_id = NULL` 宁缺勿错」，`limit(50)` 换成时间窗（scope 内 + 前 45 天）。dev 库里同设备 12 字前缀互撞 3 对、12.2% 的内容卷进碰撞，且撞的全是「金额陈述/二选一」那一路——而臂在账号内交替，相邻内容天然属于不同臂，所以错归属**与臂相关，是有偏不是噪声**，方向永远指向零、A/A 也发现不了。宁缺勿错把有偏换成随机缺失，对测量是净收益。
- **`top_posts_for_remix` 有一处会随采集定时化爆掉**：它 `select(PostMetric).where(body != "").order_by(captured_at.desc()).all()`，**没有 LIMIT**，body 上限 3000 字。今天 638 行无所谓；定时采集后按 500 行/天算，一年 18 万行 = 一次调用往内存里拉 100MB+ 并全量排序，而调用点在 `POST /supply/run`（请求内跑生成循环）和 `/content/engine/preview`，单 worker。加 `captured_at` 截断 + limit，一行。

## 三、内容类型体系

**两级。** 这是从「分层归因」那版嫁接过来的，因为配额和写作对「类型」的要求互相矛盾：配额要少（否则每桶攒不到样本）、边界要几个月不变、要能从任意一条观测到的帖子文本判出来；写作要多、要可增删、只需在生成时指定。

### 第一级：内容风格（配额单位，闭集，代码里写死枚举）

给运营看的名字：**纠结对比 / 日常讲述 / 清单行情**。

| 风格 | 含哪几路 | n | 同号同期评论位次 |
|---|---|---|---|
| 纠结对比 | 两难选择、踩坑复盘 | 171 | 0.562 [0.521, 0.602] |
| 日常讲述 | 开口提问、转述别人、数字摆事实、普通陈述 | 645 | 0.494 |
| 清单行情 | 清单攻略、行情通报 | 78 | 0.413 [0.353, 0.473] |

**这张表在 note 级重算前是待验证的**（见第一节第 2 条）。判定规则写死：重算后「纠结对比 vs 日常讲述」的位次差 CI 不含 0 → 三档成立；含 0 → 退回两档（纠结对比 / 其余）。这个判定必须在 P1 做完才能进 P3，不许跳。

不给 8 类各写一套提示词：8 类里 5 类的位次 CI 跨 0.5，28 对两两比较过 Holm 只剩 2 对，折半复现中间 6 类在洗牌。**而且三档本身是看过 8 类结果之后合出来的，报出来的 CI 是挑选后的 CI**——所以三档冻结之后要拿上线后的新数据再估一次，不能当既成事实。

枚举写死在 `backend/app/core/content_taxonomy.py`，**不能是自由文本**，否则一年后库里 40 个近义类型。「新增一档」= 一次发版，这是特性不是缺陷。

### 第二级：写法（写作单位，挂在某一档下，可增删，永不单独拿配额也永不拿效果判决）

不是标签，是结构规格，四个槽位：钩子形态（疑问开头 / 数字对撞 / 第三方引语 / 结果先行）、对立面（写不写出两个互斥选项及代价）、数字位置（封面首句 / 正文首段 / 不出现）、结尾动作（抛回一个具体问题 / 无）。

### 打标

- **存量：正则优先，不用模型。** 产出上面那张表的分类器本身就是标题正则。它确定性、可重跑、零成本。**必须连同 50 条人工金标准一起提交进 `tools/`**——它是本方案可复现性主张的全部依据，今天只是一段口述。正则未命中的残余才交 DeepSeek，标 `source='llm'`。
- **`PostMetric` 也要打标**，不能只靠 join。`content_id` 为空但有正文的行是样本池主力（447/638），它们没有 `ContentItem`。
- **新内容：生成时下发（declared）+ 落库后正则复核（observed）**，两者不一致标 flag。**declared 与 observed 的一致率就是写法层最核心的过程指标**——让生成器自报类型而不复核，提示词漂移永远发现不了。
- 打标时机必须是生成时，因为配额只能在生成端执行。今天类型分布极不均：数字摆事实 248 条 vs 清单攻略 18 条，**13.8 倍**；清单类 0.26 条/天 = 3.8 天才 1 条，按现速率要 51.5 个月才能对它下结论。**配额的第一个收益不是提升流量，是把不可测的类变成可测的类。**

## 四、分析层用什么模型

**现有 DeepSeek，一个不加。** 注意生产实际跑的是 `deepseek-v4-pro`（推理模型），不是 `config.py` 默认的 flash——记账 bug 必修，否则「哪版提示词更划算」的唯一依据是错的。

三个用途：
1. **打标残余**（正则未命中的部分）。20 条一批，输入只给封面 + 标题 + 正文前 200 字，温度 0，pin 住模型名和 prompt 写进 `label_version`。存量一次性 ¥0.2 量级。
2. **周度提示词提议**（见第六节）。输入不是原文堆，是结构化对照表。
3. **影子测试不需要模型判分**——四个指标全是确定性的。

**成本不是约束，时延是。** 实测一批 3 条草稿输入约 822 token、输出 1662 token，¥0.004；按档分化每档多喂 10 条样本 ≈ 多 1500 token 输入 ≈ ¥0.0015。就算 3 档各一套 prompt + 样本，每天几分钱。真正的约束是 `POST /supply/run` 在**请求里**跑完整的多城市生成循环，`deepseek` timeout 300s，按档分化会把循环次数乘上档数——**这条路必须先改成投队列**（现成的 `_content_supply_loop` 就是），不能直接乘上去。

## 五、多模态：本期不做，理由不是「没时间」

四条判断依据，都是代码事实：

1. **图像输入不存在。** 大字报封面是抖音/小红书自己渲染的：`TaskCoordinator.kt:293` 的注释就是 "Use the system-recommended template"，`composeBody` 只做一件事——把 `coverTitle` 填进平台的写文字卡片。字号、配色、留白、版式 100% 由平台决定。全项目没有任何模板选择代码。我们手上唯一拍到真实渲染的是发布流程截图，而 dev 库 `screenshot` 表 **0 行**、目录空（每任务只留 12 张 + `retention_days=30` + purge 连文件删）。
2. **输出没有落点。** 就算得出「这类结构配大字号短句更好」，端上没有按类型选模板的入口，`ContentItem` 上也没有承载模板选择的字段。
3. **大字报的「结构」是文本，不是图像。** 用户第 3 条想用多模态分析「框架/结构」——而那个框架就是那段文字本身。让视觉模型去看同一段文字的照片，只会多一层 OCR 损耗，增量是负的。
4. **选型问题从代码里回答不了。** 生产网关是 `https://chatgpt.58corp.com/api/v3`，不是 DeepSeek 公网 API；实测 `GET /models` 返回 **302 → passport.58corp.com/login**，模型目录在内网 SSO 后面，程序取不到。

**什么条件下才启动**（前三条必须同时满足）：服务端自己渲染并存档大字报封面（有图像输入）；端上能按内容类型选模板（结论有落点，需真机验证）；单档单臂月产能 ≥ 60 条（判定周期压到 8 周内）。独立触发条件：要分析**竞品**爆款（拿不到别人正文，只能截图）——那时多模态是必需的，但那是另一条产品线。

**但封面质检本期就做，0 模型、0 元：**
`cover_title` 有三个互不一致的上限——提示词写【80 字以内】、`AgentTask` 允许 100、`ContentDraft`/`ContentItem` 允许 200。库里已有一条 **82 字**的封面。它在大字报卡片上是 6 号字、还是被截成半句、还是溢出，**今天没有任何人、任何日志、任何字段知道**。改法：三个上限统一到 80，服务端硬校验；再花半天从生产捞 30 张 `selecting_template` 截图人眼看一遍（第一步是一条 SQL：生产上到底还有没有这些截图）。这是 n=1 就能行动的事，不需要功效。

## 六、提示词迭代机制 + 人在哪一步

### 存储：从「一个可覆写的 key」改成「不可变版本表 + 一根活动指针」

今天最要命的一处，也是 13 处断点里**唯一时间不可逆**的：`generate_drafts` 收了 `preset_id`、用它取提示词，然后建 `ContentDraft` 时**一个字都不写**；提示词本体是 `AppSetting` 单行原地覆写、无历史表；界面上唯一的「恢复默认」回到的是内置出厂值，**不是上一版**。所以前向链路 `PostMetric → content_id → ContentItem → ContentDraft` 走到 draft 这里断掉，「这条 9.5 万浏览的爆款是哪版提示词写的」永远回答不了。**今天每生成一条草稿，这个信息就永久少一条。** 所以它排 P0，不排 P3。

新形态：`PromptVersion` 写入即冻结（编辑 = 新增一行，parent_id 指上一版），每档一根活动指针，回滚 = 指针回指。三段式：共享前言（四个字段的规格）+ 档段 + 写法段。`ContentDraft.prompt_version_id` + `ContentItem.draft_id`。

顺带堵一个洞：`PUT /content/engine/prompt` 只挂了 router 级 `require_admin`，没有像 aiconfig 那样加 `require_admin_role`——**任何 operator 令牌都能改掉全局提示词**。建版权限可以给 operator，提成主版必须 admin。

### 两层迭代（嫁接自「分层归因」那版）

**写法层：影子测试，当天出结果。**
新版和当前版各生成草稿，**不入池不发布**，只算确定性指标：类型命中率（declared vs observed）、规格违规率（长度/地名/时效/封面撞库）、查重相似度分布、封面长度分布。

- **n = 200/臂，不是 30。** 原设计的 n=30 在精确 Fisher 双侧下：0.90 vs 0.60 功效只有 0.705，现实幅度 0.85 vs 0.72 只有 **0.15**、0.80 vs 0.70 只有 0.09。也就是除了灾难级差异永远判 same——而这是写法层唯一的判决工具。n=200/臂 对 0.85 vs 0.72 功效 0.87，一次 ¥0.55。成本不是约束，别在这里省。
- **影子稿必须四处隔离**：从 `list_drafts` 默认列表过滤掉（否则运营的待审量从 13.5 条/天涨到 20+，而多出来的既不该采纳也不该拒绝）、从 `draft_stats` 排除（否则累计成本和状态分布跟着脏）、用独立 status 从 `_dup_corpus` 排除（见第一节第 10 条）、在 `accept_draft` 里硬拒。
- 「人工零改采纳率」**不能进影子记分卡**（影子稿永远不会被 accept，这个指标恒为 0/0）。它只能从线上真稿按 `prompt_version_id` 分组算，属于效果层的辅助指标。

**效果层：6–7 周一次主版更替。** 见第七节。

### 人介入三处，其余全自动

1. **影子测试结果确认**：模型或人产出的新版落成 `PromptVersion(status='proposed')`，人看 diff + 影子对比表，点「设为挑战版」才进线上 A/B。**proposed 永不自动上线。**
2. **期末判决后点「晋升为主版」**：界面显示配对差、n、CI，人点确认。
3. **月度配额拍板**：系统给建议值 + CI + n，人可改任一档但不能低于 20% 保底。

自动提议的输入（周五 09:30 周报之后跑，`to_thread`）：当前该档提示词全文 + 上一版的 changelog/假设/**实测结果** + 该档上周同号同期位次头尾各 10 条（不是全站 top10）+ 上周机器闸驳回理由 top5 + 上周人工拒绝理由 top5 + 人工编辑率与 3 个改动最大的 before/after + 人填的「本周重点」（可空，这是唯一让业务判断进入闭环的入口）。输出硬 schema：`{tier, system_prompt, changelog, hypothesis, expected_metric, expected_delta}`。`hypothesis` 和 `expected_delta` 是硬要求，冻进 `PromptVersion`，期末拿实测对照——**模型预测的方向准不准本身是一个可测量的量，连续 3 次方向错就停掉自动提议**。

### 护栏（原设计这里有致命，已重做）

原方案的四条护栏用「相对对照臂 2 倍 / +20pp 的滚动窗口」，蒙特卡洛在**两臂完全相同**时 12 周误停概率 **1.000**，中位在每臂第 28–37 条就触发。也就是挑战臂永远到不了判决所需的样本量，于是「12 周从未晋升」必然成立，于是按预注册规则「提示词优化不是那个杠杆」被自动判定——**那个结论是阈值写出来的，不是数据得出的。** 重做如下：

**A. 规格类（绝对阈值，不与对照臂比较，不做统计检验，触发即停臂）**
- 地名泄漏 > 0 条（**前提：先给 `city_tokens` 一个代码内默认词表**，否则这条是空转）
- 封面 > 80 字 > 0 条
- 正文长度越界率 > 5%
- 查重命中率（`dup_score ≥ 0.90`）> 15%

**B. 品牌类（人工，触发即停臂，不需要统计）**
每天在企微群播 **3 条随机抽检的完整正文**（不只封面）；挑战臂期间提到 10 条。运营判定任一条「在带节奏」→ 立即停臂。理由见第一节第 14 条：自动路径每天十几条无人过目就上真号，而主指标是评论数、A 档就叫纠结对比、样本是评论远高于点赞的引战型结构——**目标函数的最优解就是吵架量**。这条护栏成本 10 分钟/周，是全案性价比最高的一条，缺了它这个方案不该签。同时：A 档配额上限 40%，不允许 argmax 推到 100%；清单行情不归零。

**C. 统计类（只保留一条，预注册序贯边界）**
块内配对差 d < 0 且**单侧 p < 0.005** 且 n_pairs ≥ 40 → 停臂。零假设下总误停率 < 2%（对比原设计的 1.000）。不用「位次 CI 上界 < 0.5」——0.5 不是分档条件秩的正确零假设，B 档在配额从 19% 调到 40% 后会机械下移到 0.472，代入原规则一个完全无害的挑战版在 B 档有 35–48%、C 档 66–83% 的概率被杀掉。

**护栏防止变差，实验证明变好。这个不对称是设计的一部分。**

## 七、测量设计

这一节写不实，整个方案就是漂移。

### 分析单元与主指标

- **单元 = note（帖），不是快照行。** 所有历史结论按 note 级重算（第一节第 2 条）。
- **块 = (账号, ISO 周)。** 账号身份走 `(device_id, platform) → DeviceAccount` 反查（`account_id` 是空列）。
- **主指标：`log10(1 + comments)`**，取发布后次日首采读数（`age_hours ∈ [14, 30)`）。类型对评论的解释力是浏览量的 2.6 倍，类内 sd 0.611 vs 0.905，同样结论少要约 2 倍样本；而且对得上业务事实（头部内容 155 赞/312 评、97 赞/367 评）。现在的 `engagement = likes+collects+comments` 把三个信噪比完全不同的量等权相加，白白稀释信号。
- **换主指标前必须先在生产分布上量一遍评论的零膨胀。** dev 库 22.6% 评论为 0、33.7% ≤ 2；`log10(1+comments)` 在 0 上有点质量，sd 变小有一部分来自地板截断，而地板上的样本彼此无法排序、在位次法里进同一个 tie 块。生产中位 11000 下应该好得多，但这是必须实测的一步，不能只比 sd。
- 副指标（只报不判）：浏览位次、评论/浏览比、`age_hours`（作为两臂平衡检查）。浏览量 ≥ 10000 的样本 100% 是整千数、只有 51 个可分辨档位，秩检验里 tie 很多，所以它只能当副指标。

### 分组：块内交替，绝不按账号切

按账号分臂的后果：σ_account = 0.378 log10，22 个账号每臂 11 个，两臂均值差仅由账号构成产生的标准误 = 0.161 log10 = **1.45x**，2se = 2.10x。**两个完全相同的提示词，按账号分组有约 32% 的概率报出 ±45% 以上的差、5% 的概率报出 ±110%。** 而你要检出的是 1.5x。这不是不够严谨，是输出与真相无关。

可行性：类型 × 账号 Cramér V = 0.163，22 个账号里 8 个覆盖全部 8 类 → 类型与账号基本正交，不存在「这个号只适合某类内容」的结构约束，账号只贡献噪声不贡献偏倚。

块是「周」不是「天」：13.5 条/天 ÷ 22 账号 = 0.61 条/账号/天，一天凑不出一对；而周同时把周效应差掉——全站周中位数在 W28 = 10000 → W29 = 3050 → W33 = 8291 → W36 = 2188 之间摆 **4.6 倍**，前后对比在这个漂移上 100% 是噪声。

**arm 在「内容被消费进发布任务」那一刻盖章，不用 `published_at` 计数。** `published_at` 只在成功时写，失败会置回 None，而 `published_device_id` 是消费时就写的——按 `published_at` 计数会让在途和失败重发的从交替计数里消失、arm 漂。失败回池必须重新盖章。`platform == 'both'` 的扇出和将来的双投必须按 `(content_id, device_id)` 分组分析，不能用 `content_performance` 的 `latest.setdefault`（它每个 content_id 只留一条最新快照，第二台设备的读数被静默丢掉）。

### 估计量

**块内按 `1/(1/nA + 1/nB)` 加权 = 带块固定效应的 OLS。** 不用无权的「块均值差的均值」——按 dev 库真实的块大小分布实测，无权版 se 比理想值高 **11.9%**（若分布更偏则高 34%），等于白扔 25–79% 的样本。修法是一行权重，免费。Wilcoxon 符号秩留着当稳健性检查，方向不一致就判无结论，但不是主检验。

**统计检验不进生产 app。** `requirements.txt` 里没有 numpy/scipy，而生产是 PyInstaller 冻结分发、运营侧已经在被 Defender 隔离未签名 exe。生产 app 只算加权均值差 + 标准误（纯算术，df > 30 用 1.96），完整检验（Kruskal / bootstrap / 卡方 / spearman）放 `tools/` 下的独立脚本，在分析机上跑。这样绕开打包问题，也顺便解决「分析不可复现」。Pillow 已装在 venv 但未 pin，补一行。

### 样本量与周期（诚实版）

理想：`n_pairs = 7.849 × 2 × σ_within² / log10(1.5)²`，σ_within(comments) ≈ 0.551 → **154 对 = 308 条 usable**。

回代真实损耗：
- 归因完整率 0.927（生产 924/997），匹配改严后可能掉到 0.80
- `arm_forced`（缺货降级 + 运营手工指定）0.90
- σ 是外推值（正确基数应是整体 comments sd ≈ 0.630 → σ_within ≈ 0.568，n 从 154 到 164）

名义条数 ≈ 164 × 2 / (0.80 × 0.90) ≈ **455 条 ≈ 4.8 周**。给余量，**第一轮定 6 周，power ≈ 0.85**。

**明确否掉「4 周」这个数字**：4 周 = 378 条名义 → usable 约 272–315，power **0.72–0.81**。也就是真实效应恰好等于设计值 1.5x 时，第一轮有 2–4 成概率跑出「无结论」——而「无结论」正是最会让人觉得系统没用的那个结果。

**同时明确物理上限**：1.2 倍及以下的改进这套系统测不出来（需 763 对 ≈ 16–18 周）。所以「微调措辞」类改动**直接拒收，不进实验**，每轮实验的机会成本是 6 周。这个上限来自残差 ≥ 76.7% 的推荐随机性，不是设计缺陷——按账号+周做区组只能把所需样本降到 81%（省 19%），加账号、加城市都不省钱。

### estimand 必须写清：这是 as-published 效应，不是 ITT

随机化发生在 draft，测量只发生在「被采纳且被发布」的子集上。dev 库实测衰减：95 条草稿里 rejected 22（23.2%）、pending 5；`contentitem` 73 条里 pending 24（32.9%）从未发布。而丢失机制正是运营看着草稿好坏做的判断——这是 post-treatment selection。方向不可预测：挑战版若产出更极端的草稿、运营砍掉最差的，存活样本被挑成精英，判决会把「运营的筛选能力」记成「提示词更好」。

处理方式（不含糊过去）：
- **明确定义 estimand 为「这一版提示词写出的、且通过人工筛选与编辑的内容」的效应。** 这恰好是运营真实关心、也是可行动的口径。写进判决报告标题。
- **两臂的人工拒绝率、编辑率必须一起报**。若两臂拒绝率差 > 10pp 或编辑率差 > 20pp → **判无结论**（选择性不对称，比较不成立）。
- 采纳时的正文改写要留 `original_body`（今天 onAccept 先 PATCH 覆写再 accept，AI 原文被就地覆盖），否则被测的文本不是被随机化的那版文本。
- 分臂标签对运营可见，没有盲法安排，预期偏倚无法排除。这一条如实记录在方法说明里。

### 判据（开跑前写死，跑完只读不改）

- **采纳**：加权配对差的 95% CI 下界 > 0，且 Wilcoxon 方向一致，且规格/品牌护栏未触发，且两臂筛选强度差在阈值内。
- **回滚**：CI 上界 < 0，或任一护栏触发。
- **无结论**：CI 跨 0 → 保留主版，挑战版归档，并把「这个方向没有可检出效果」显式记下来（否则同一个方向会被反复试）。
- **只看两次**：第 3 周中期（只能停不能过，用序贯边界 C）+ 期末一次。
- **不许延长实验捞显著。** 延长到显著等于把 α 从 0.05 抬到实际 0.15–0.30，系统会开始稳定采纳无效改动而没人能发现。到期无结论就是无结论。
- **序贯采纳的累积假阳性**：单轮误采 2.5%，一年约 8 轮 → 至少一次误采约 18%，而主版是粘性的。所以采纳用**单侧 α = 0.025**，且新主版要在下一轮的确认性对照里不显著变差。

### 配额层的测量（这里原设计有致命，已重做）

单元内位次是**零和度量**：任一单元内均值恒为 0.5，所以「全站按条数加权平均位次没有下降」这条成功条件**恒等式成立、永不触发**；而且把纠结对比的配额从 20% 抬到 35%，它的测得位次会机械回落约 0.010（占阈值余量的 1/4），台账会把自己的成功读成衰减。

改法两条：
- **配额切换用集群随机**：一半账号跑新配额、一半保持现状，2–4 周后交叉。成本同样是 0 台额外手机，却把一个不可证伪的全局变更变成可判决的。
- **加绝对量护栏**：账号级周中位评论数（不是位次）。相对位次对全体等比下滑完全免疫，必须有一个绝对量的眼睛。

### A/A 空跑 1 周，不可省

两臂用同一版提示词的两份拷贝，全链路照跑。预期 CI 跨 0 且 |d| < 0.10。**如果 A/A 报出显著差异，说明分组或归因有 bug（最可能三个：pick_arm 种子重启后不稳、arm_forced 没正确剔除、发布时段在两臂间失衡），先修再谈 A/B。** 一个报得出假效应的实验台比没有实验台更危险。A/A 的第二个用途是量出评论数的真实块内配对 σ，替掉上面那个外推值、重算实验长度——所以它不是浪费一周,是用一周买掉两个未知数。

### 三条持续校验

1. **归因完整率** = 进判据条数 / 已发布条数，< 85% 就查。
2. **两臂平衡**：风格构成、城市构成、**发布时段构成**各做一次卡方，p < 0.05 在报告里显式标注。发布时段这项特别重要：块是「周」，周效应被吸收了但**日内时段效应没被吸收**，而 `plan_times` 是 `windows[index % len(windows)]`——序号确定性地决定时段。
3. **成熟度**：comments@D+1 与 D+7 的 spearman。dev 库实测（47 条跨度 ≥3 天的帖）**rho = 0.960**，远高于 0.80 阈值——所以「主指标要挪到 D+7、每轮加 6 天」这个原方案称为最大单点风险的事，大概率不会发生。这是白捡的一个确认。

### 效果榜口径变更

返回值加 `device_id / account_id / published_at / content_type / prompt_version_id / arm / age_hours / unit_rank`；默认排序从 engagement 换成同号同期位次；加 `order=none` 取全口径。今天返回的 dict 里根本没有账号字段——**运营和模型看的「浏览量排行榜」实质是账号排行榜**。界面文案：列名叫「在这个号这周里排第几」；风格叫「纠结对比 / 日常讲述 / 清单行情」；被排除的那部分写「部分内容因同期作品太少，暂不参与排名」。

### Exit criteria（现在就写死）

第一轮 A/B 起算 **12 周**，若从未发生过一次晋升，停止提示词自动优化，力气转向两个更大的杠杆：吞吐（13.5 → 25 条/天，样本量线性买检出能力）和账号侧。**这个方案的价值在于它能给出这个答案，而不在于答案一定是「提示词优化有用」。一个不能得出否定结论的闭环不是闭环。**

## 九、从落选方案嫁接了什么

- **「最小闭环」那版**：`MetricsRun` 一张表同时解决幂等/凭据/告警/错峰；每期 revert 用配置开关而不是回滚代码；exit criteria 与元层测量（模型预测方向连错 3 次就停）。**没嫁接它的四条护栏原始阈值**——那套滚动窗口比较在零效应下 12 周误停概率 1.000，会自己造出「12 周无晋升」的结论。
- **「分层归因」那版**：类型分两级（配额层的闭集 3 档 / 写作层的 recipe）；两层用不同证据不同频率不同人；**影子测试**用确定性过程指标当天迭代——这一条直接解决了「效果 A/B 6 周一轮、日常没法迭代」的死结，是本方案能动起来的关键。它的配额层测量被我换成集群随机 + 绝对量护栏（原设计的位次台账在零和度量上不可证伪）。
- **「封面留证」那版**：Phase 0 那个可能杀死自己的 0 元实验（先看 30 张截图再决定要不要建管道）；多模态降级成质检 + 仪器；`cover_title` 三个上限不一致和那条 82 字封面；网关 `GET /models` → 302 → SSO 这个硬事实——它把「用哪个多模态模型」从一个可以糊过去的问题变成一个必须由人去查的行动项。
- **主干「同号配对」那版**：块内交替不按账号切臂（唯一不可逆的架构决定）；块 = (账号, ISO 周)；主指标换评论数；A/A 不可省；预注册判据 + 不许延长捞显著。

## 十、这个方案牺牲了什么

1. **不交付「模型自动按类型优化提示词并上线」。** 用户第 4、6 条要的是自动，我给的是「模型提议 + 人点两次」。理由是数据：档级 A/B 要 3–6 个月，而一个无人看管的自动循环会把 4.6 倍的周漂移学成规律。
2. **不交付多模态。** 用户第 3 条明确要，我明确说不做，并写清了四条判断依据和三条启动条件。
3. **风格最多 3 档，可能只有 2 档。** 由 P1 的 note 级重算决定，规则已写死。运营会觉得颗粒度太粗——「开口提问」和「转述别人」他们直觉上有区别，但这两类的 CI 都跨 0.5。8 类作为记录标签保留，schema 上留好了位置。
4. **效果判决 6–7 周，不是隔天。** 护栏能当天发现变差，证明变好没有捷径。1.2 倍以下的改进直接拒收。
5. **estimand 是 as-published 不是 ITT。** 我们测的是「这版提示词写出的、且通过人工筛选的内容」的效应，不是提示词的纯效应。这是诚实的口径，不是漂亮的口径。
6. **配额切换要用集群随机**，所以有一半账号在 2–4 周内跑的是旧配额，产能上有一点损失换来可证伪。
7. **判据用评论数，而对客户汇报用浏览量。** 会出现「CI 说新写法好 34%，可是浏览量榜上看不出来」。实验页要同时显示两个数并说明哪个是判据，对外口径要分开讲。
8. **小红书本期只享受采集修复。** 全库 xhs 效果样本 2 条、匹配率 4%，所有类型/配额/提示词结论只对抖音成立。
9. **影子测试每周多约 400 条草稿**入库，库增长 + 必须四处隔离干净，隔离漏一处就是内容池水位事故。
10. **不修的四件**：`retention_days=30` 导致的数字冻结（爆款长尾恰好在 30 天之后，所以「哪类内容长尾更久」本期回答不了）；`PostMetric.shares`（界面撤列）；`record_metrics` unchanged 分支就地改老行且不刷 `captured_at`；双投对照臂（所以「账号 vs 内容」仍是统计分解不是实测）。
11. **最诚实的一条**：残差 76.7%，跑满 12 周有真实概率得出「三档之间无可复现差异」。届时正确动作是停掉自动 review、转向吞吐和账号侧。

# 附：完整性批评（独立 agent，18 条）

按重要性排序。每条我都在代码/数据里核过；`file:line` 是我这次实际读到的。

**1. 拍板项 1 的论证方向是反的，而测量那一节的 age 窗口悄悄依赖它的结果。**
`publish_windows` 默认空串，`_due_by_plan` 在 slots 为空时直接 `return True`（`backend/app/services/tasks.py:271-290`），`publish.py:31` 自己把这个状态命名为 `unrestricted`——"手机一空就发"。所以生产上这个键若是空的，结论不是方案写的"10-11 就没有撞车问题，(b) 直接可行"，而是**全天没有一个安全小时**，09:00 相对 10:00 收益为零，唯一有效防撞只有设备级互斥。更要紧的是主指标取 `age_hours ∈ [14,30)`：09:00 采昨天的帖，age = 33h − 发布小时，落窗要求发布时间在 03:00–19:00；发布不限时段时按均匀分布约 **33% 的样本被静默剔除**，而测量那一节从没说它依赖 1 号拍板。补：把这个键的查询从"P0.5 的 0 元核查"提成 P2 和 P4 的**前置门**——空则先设时段，或把窗口放宽到 [8,34) 并接受年龄不齐。

**2. 这 13.5 条/天到底由哪条路径发出，方案没查；如果是排期路径，随机化根本不成立。**
`tasks.py:412` 的注释原文是「因为自动发布从来没在生产上开过，这个洞一直没暴露」，dev 库 27 个 `deviceaccount` 的 `auto_publish` 全为 0。真正在用的大概率是 `schedule_posts`（`tasks.py:679-740`），它允许运营**逐槽 pin 一个 content_id**（`:690`「lets the operator pin a specific content piece to a slot」），而且整条路径不过 `_due_by_plan`、不过 `max_concurrent_publishes`。运营手挑内容就是按他自己对好坏的判断分臂——这不是 `arm_forced` 10% 的量级问题，是分组机制失效。补：P0.5 加查生产 `auto_publish` 计数与最近 200 条 PublishTask 的 `publish_mode`/`scheduled_at` 分布；若排期是主路径，P4 必须先把"未 pin 的槽由后端按臂选"做成默认，pinned 槽整条剔除并把占比上报。

**3. arm 是"内容自带的属性"还是"消费时的随机标签"，方案两种说法混着用，落地形态因此缺失。**
提示词版本决定内容，arm 不可能在消费时"盖章"；能做的只是"每个发布槽从两个池里选一个"，那 `_match_content`（`tasks.py:437-458`，纯 `created_at` FIFO + 城市优先 + 通用回落）必须改成按臂取最老，且生成端必须保证每城每档两臂都有货。`arm_forced=0.90` 没有任何依据，也没算碎片化：3 档 × 2 臂 × 城市，而库存目标是 `min_days=3`、`batch_cap=10`（`content_supply.py:29-33`），小城市每桶只剩 2-3 篇。补：写明"随机化单元 = 发布槽"；生成端按 (城市 × 档 × 臂) 下配额、`min_days` 提到 5；`arm_forced` 由 A/A 实测，>25% 先扩池再开 A/B。

**4. 用户第 5 条被缩窄了：真正的"人工生成"有两条入口，方案一条都没提。**
`POST /content`（`content.py:56-71`）和 `POST /content/import`（CSV 批量，`content.py:164-200`）直接建 ContentItem——不过 `check_draft`、不过查重、没有 content_type，CSV 连 platform 都不收（默认 douyin）。方案里的"人工路径"全部指 `accept_draft`。后果：运营自己写/导入的内容类型为空 → 不进配额、不进类型分面、不带 prompt_version/arm，却照样吃发布名额和 A/B 分母（dev 库 10/73 = 14% 的 ContentItem 不来自任何草稿）。补：两个入口都必填 content_type + 过长度/地名/时效三闸 + 打 `origin='manual'` 并在分析里显式剔除；排期弹窗的内容选择器也要显示类型，否则运营无法"产出不同类型"。

**5. 设备"在忙"的模型漏掉三件事，而漏掉的正是历史事故的那条路径。**
方案给 `claim`（`AgentForegroundService.kt:186`）加 `metricsBusy` + `collecting`，但同一条 else-if 链上的 `readAccountSequence()`(`:193/:274`)、`readGroupsSequence()`(`:199/:885`)、`readXhsAccountSequence()`(`:206/:334`) **全部内联跑在 ticker 线程上**（只有回采被搬进了 `Thread{}`，见 `:379-391` 的注释），群列表那一轮 8 处 `Thread.sleep` + 3 轮刷新轻易超过 `device_offline_seconds=45`——这就是"阻塞心跳 → 误判掉线 → 运营刷机丢登录态"的未修复同类。后端下发采集时手机可能正卡在这里，run 直接成孤儿。补：三个 sequence 一起搬线程并纳入同一个 busy 标志（心跳别只报 collecting）；lease 回收器要覆盖"派了但手机在忙别的"。

**6. 影子测试 200/臂在现有实现上不可能一次调用完成，执行形态和失败语义都缺。**
`dto.py:122` 的 `count` 是 `le=10`，`content_engine.py:312` 再 clamp 一次 `min(count,10)`——200 条 = 每臂 20 次串行调用、每轮 40 次；生产模型是 `deepseek-v4-pro`（推理模型，`appsetting.deepseek_model` 实测值），单次 timeout 300s，一轮影子实际是 30-60 分钟的后台作业。方案把它当"点一下当天出结果"，没有队列、没有进度、也没有"A 臂 200 条 / B 臂 120 条就挂了"的处理（不平衡两臂不能比）。补：走 `_content_supply_loop` 那套 to_thread 队列 + 一张 run 表记 requested/completed/failed，两臂完成数差 >5% 本轮判无效。

**7. 影子稿必须同时"排除出查重语料"和"被查重指标度量"，这两条互相矛盾。**
`_dup_corpus`（`content_engine.py:40-53`）取非 rejected 草稿 400 条；方案让影子稿用独立 status 排除以保护内容池——那"查重相似度分布"这个影子记分卡指标就失去了比较对象，同臂 20 个批次之间的重复完全看不见（批内语料只覆盖 10 条）。补：影子跑用一份专用语料 = 真实池 + 本臂本轮已生成的影子稿，与生产语料物理隔离。

**8. 影子污染的第 5 个地方没列到：企微周报的 AI 段。**
`notify_sweep.py:1076-1081` 按 `created_at` 时间窗直接数 ContentDraft，**没有 status 过滤**。每周多 400 条影子稿，群里会播"本周 AI 写了 494 篇"。方案只列了 `list_drafts` / `draft_stats` / `_dup_corpus` / `accept_draft` 四处。补：第五处加过滤，并把"周报数字有没有变"写进 P3 验收（群是运营的主界面）。

**9. σ 是外推值，dev 数据给出的值高 36%，而"6 周"却被写成了要现在拍的板。**
我按 note 级重算 dev 库（255 条 note = 每 (device,platform,title) 取最新一行）：`sd log10(1+comments)=0.857`、`sd log10(views)=1.109`，比值 0.77——不是方案的 0.611/0.905=0.675，评论省的样本是 1.7 倍不是 2.19 倍；零评论占 20.8%。若块内 σ(comments) 是 0.75 而非 0.551，配对数从 154 涨到约 285、名义约 790 条 ≈ **8.4 周**，6 周的 power 掉到 0.6 上下。方案自己说 A/A 的第二个用途就是量这个 σ，却又要求先拍 6 周。补：拍板项 4 改成"下限 6 周，实际长度由 A/A 实测 σ 定；>7 周则把目标效应量放到 2.0x 或先做吞吐"。

**10. P2 的 Agent 那一半事实上不可 revert，却写成了配置开关。**
revert 写的是 `metrics:enabled=false` → Agent 36h 兜底接管。但 24h 闸门是被删掉换成 36h 的，回退后采集比今天**更稀**；要真回到今天的行为必须再推一次 37 台 APK，那是运营一整天现场操作 + 逐台复查无障碍是否解绑 + 补 `am start` + 丢登录态风险。补：如实写成"后端可停、Agent 不可回退"，并把兜底值设成 24h 而不是 36h，保证回退后不比现状差。

**11. P1、P3 各还有一处"revert 不成立"。**
① P1 把效果榜默认排序从 engagement（`metrics.py:157` 排完再截断）换成同号同期位次，revert 写"前端隐藏筛选、列留着"——隐藏筛选并不会把默认排序换回来，而默认排序才是运营每天看的那个东西；② P3 给 `_dup_corpus` 加 `order_by(id.desc())` 不在任何开关后面，它直接改变哪些草稿被判重，而方案自己论证过这会拖内容池水位。补：各配一个 AppSetting（`perf:rank_mode`、`dup:corpus_mode`），默认值切换与代码上线分两次做。

**12. 账号身份会被就地覆盖，块的主键其实是手机不是号。**
`PostMetric.account_id` 全库 0/638（`metrics.py` 里根本不写这一列），所以块只能靠 `(device_id, platform)` 反查 DeviceAccount；而 `upsert_account`（`accounts.py:26-30`）在同一行上直接覆盖 nickname/account_id。刷机重登换了号，块主键不变、历史数据被当成同一个号——而刷机在这套系统里是常规动作。补：P0 就给 PublishTask 与 PostMetric 各存一份当时的 account_id 快照，DeviceAccount 换号时新建一行、旧行标 retired，块主键用快照不用反查。

**13. `platform='both'` 的扇出制造同臂内强相关，方案只说了分组口径、没说方差。**
一条内容扇出成 2 个任务（`tasks.py:549-560`，`_find_publish_account` 还优先同一台手机），两条观测是**同一段文字**，ICC 接近"同帖多快照"的量级——正是方案在 note vs 行那条上抓到的错误的另一个版本。而 `content_performance` 的 `latest.setdefault(m.content_id, m)`（`metrics.py:127`）会把第二台设备的读数直接丢掉。补：分析时把同 content_id 的多台观测折成一个簇（或只留第一台），并修 setdefault 那一行。

**14. P4 要跑第一轮 A/B，但"第一版三套档段提示词由谁写"没有落点。**
自动提议在 P5（最后一期），P4 的挑战版没有作者。补：P4 前加一件明确的人工工作项——用 P1 的三档 + 头尾各 10 条真实样本人手写 3 段档段文案，并当成第一版的 changelog/hypothesis 基线，否则 P4 会因为没有挑战版而空转。

**15. 上线动作本身一天都没排：迁移、双前端、部署窗口。**
方案要加 2 张新表 + 3 张表各 3-6 列，而迁移机制是 `db/session.py:52` 的 `create_all` + `:120-166` 一段手写幂等 ALTER，没有 Alembic、没有 schema 版本号、没有备份步骤；生产是 PyInstaller 冻结的 exe 跑在笔记本上、37 台手机 15 秒一次心跳、开机自启；前端还必须出两份构建（桌面版 / 浏览器版）。补：每期固定收尾"停机窗口 + 先复制一份 agent.db + 迁移后跑一次列校验 + 两份前端各点一遍"，按 0.5 人日/期计入。

**16. 小红书不是"只享受采集修复"，它在稀释实验分母。**
dev 库有 7 个 xhs 账号、10 篇 xhs 内容 + 2 篇 both、321 行 xhs 快照（其中 **106 行 body 为空 = 33%**，正则打标只能靠标题）；生产 xhs 效果样本只有 2 条、匹配率 4%。只要 xhs 账号在发，这些发布就占名额、进不了判据。补：P4 期间明确"xhs 不参与实验"（xhs/both 内容不打 arm），并把它占掉的名额算进损耗——0.80×0.90 之外还要再乘一个约 0.85。

**17. 查重会随影子测试变成 CPU 大户，而这台机是单进程 + GIL。**
`_best_dup` 是 O(新 × 语料) 的 `SequenceMatcher`；我实测每次比较 0.13ms（300 字中文），一轮影子 400 条 × 800 语料 + 批内 ≈ 40 万次 ≈ **1 分钟纯 CPU**（正文更长按平方翻倍）。它在 to_thread 里不会按住事件循环，但 CPU-bound 线程照样按 5ms 抢 GIL，表现是这一分钟全站请求一起变慢——与硬约束里那条事故同症状、不同成因，而"零网络调用"这条红线没覆盖它。补：语料先按长度/标题粗筛或换 rapidfuzz，影子跑限夜间。

**18. 周采集的产物用途没有定义。**
窗口和 scope 都给了，但没说这批数据做什么：同一批里最老的是 D+8、最新的是 D+1，年龄跨 7 天；而"成熟度校验 D+1 vs D+7"需要 D+7 读数，按这个设计每周只有约 1/7 的帖子拿得到。补：把周采集的产物明确成"发布后 7 天读数"这一列（只对上周五那批成立），或者改成"7 天前那一天"的 D+7 专采，别和"上周五到本周四"混成一批。

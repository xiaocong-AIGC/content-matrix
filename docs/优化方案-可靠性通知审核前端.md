# 图文矩阵营销平台 · 优化方案（可排期版）

> 适用范围：37 台云机 / 22 个抖音号 / 发布室后端 + 控制台 + Android Agent
> 本文档由四份领域方案（发布可靠性、通知、AI 自动审核、前端统一）+ 两轮挑刺整合而成，**冲突处已按代码事实裁决**，标注了裁决理由。
> 口径纠正：`/content/generate` **不是零鉴权**，它挂在 `backend/app/api/v1/router.py:26` 的 router 级 `require_admin` 下（operator 令牌即可调用）。真正的口子是它没有速率/并发限制。

## 1. 一段话结论

84% 的图文发布失败（42/50）是 `confirmation_timeout`，根因不在"人没来"，而在 `AgentForegroundService.kt` 所有启动点只加 `FLAG_ACTIVITY_NEW_TASK`——对已在运行的抖音等于把上次的任务栈调回前台，于是任务从直播间/评论区开始跑、`PageRecognizer` 只认 8 页全落 UNKNOWN、自愈失败转人工、人不来、10 分钟后判失败并把设备堵满 10 分钟；但**在动手改这条主线之前，必须先修四个地基 bug**——`_ACTIVE_TASK_STATUSES` 把未到点排期算作 active 导致 `max_concurrent_publishes=3` 的矩阵闸永久饱和（`tasks.py:41-46 / 152-159 / 161-173`，已实机核对）、`reclaim_expired_tasks` 不调 `_finalize_content` 导致租约超时的内容永久卡在 PUBLISHING（`tasks.py:551-598`，已核对）、`fail_stuck_confirmations` 从 `started_at` 起算导致人工窗口经常等于 0（`tasks.py:616-620`，已核对）、以及 `_finalize_content` 在失败瞬间就把内容退回池——这一条会和 180 秒后的自动重试直接撞车、造成同一文案两台机各发一遍。因此正确的落地次序是**先止血 → 再上重试引擎（含内容预留态）→ 再做归一化（按需杀进程，且必须先实机取样冷启弹窗）→ 再上前端筛选骨架 → 再上通知 → AI 自动审核放最后且首期只开自动拒不开自动通过**，全程遵守三条不可退让的纪律：**点过"发作品"之后的任何不确定一律不自动重试、任何会关闭账号 auto_publish 的判据必须连续两次命中才生效、任何收窄内容供给的规则上线前必须先跑内容池水位干跑（北京 6 个号目前专属内容为 0 条，全靠通用池）。**

## 2. 发布可靠性：归一化 + 重试

### 2.1 前置：四个地基 bug（不修则本章全部无效）

| # | Bug | 位置 | 后果 | 修法 |
|---|---|---|---|---|
| **B1** | `_ACTIVE_TASK_STATUSES` 含 QUEUED，且设备闸与矩阵闸都不看 `scheduled_at` | `tasks.py:41-46`、`152-159`、`161-173` | 未到点的排期任务被算成"正在进行"。37 台各有排期时 `cap=3` 的矩阵闸永久饱和，**重试任务永远排不进队**，且今天的自动发布本身就在被这条闸门抑制 | 两处 active 统计加 `(scheduled_at IS NULL OR scheduled_at <= now)`，与 `claim_next_task` 同口径；矩阵闸再排除 `is_retry=true` 的行 |
| **B2** | `reclaim_expired_tasks` 不调 `_finalize_content` | `tasks.py:551-598`（对比 `fail_stuck_confirmations` 在 `:638-640` 补过） | 租约超时的任务占用的 ContentItem 永久停在 PUBLISHING，既不回池也不算已发布 | 补一行 `_finalize_content(session, task, succeeded=False)` |
| **B3** | 人工窗口从 `started_at`（首次 RUNNING）起算 | `tasks.py:616-620` | 一个跑了 11 分钟才转人工的任务，下一次 60s 扫描立刻判失败，**人工窗口 = 0** | 新增 `waiting_since` 字段并改用它；历史行 NULL 时按 600s 兜底，**不要回退到 `started_at`** |
| **B4** | queued 任务无过期机制，`reclaim` 只回收 leased/running | `tasks.py:551-598` | 离线/无障碍未绑定的设备上的 queued 任务永远不回收，配合 B1 会把全矩阵饿死 | 新增 `queued_expires_at`（默认 30 分钟），在 maintenance loop 里超时判 failed 并释放 |

> **B3 与 `confirmation_timeout_seconds` 600→300 必须在同一个 commit 里**。任何一条先落地，人工窗口都会归零或翻倍。另注：`main.py:34` 的 timeout 在 while 循环外读一次，改配置必须重启后端——写进部署文档。

### 2.2 App 归一化：**按需触发**，不是每次都杀

**与初始决定的差异（需拍板，见 §9-Q1）**：原定"每次任务前都杀进程冷启"。裁决建议改为**先做一次廉价 `recognize()`，已在 HOME 且无阻断页则直接跳过归一化**。三条理由：① 84% 的失败是"不在一级页面"，反过来说相当比例的任务开局本来就在首页，白杀一次进程只多花 8-20 秒；② 冷启动是设备指纹/登录态校验最集中的时刻，37 台每天 74 次固定时段集中冷启是自动化农场的典型画像，而 `SECURITY_CHALLENGE` 被定为不可重试 + 关账号 auto_publish，一旦某次版本更新让冷启普遍触发验证，系统会在几小时内把整个矩阵的自动发布自己关光；③ `config.py:16-18` 的注释已经写明"单编排器串行 adb 拉 App 启动会排队"，这正是 lease 从 120s 放宽到 300s 的原因。

**四层手段（确定性递减）**

| 级别 | 手段 | 清进程 | 清任务栈 | 确定性 | 依赖 |
|---|---|---|---|---|---|
| P0 | 编排器 `am force-stop <pkg>` + `monkey -p <pkg> -c LAUNCHER 1` | 是（含子进程、闹钟、Service） | 是 | ~100% | adb 可达 |
| P1 | `killBackgroundProcesses(pkg)` + `NEW_TASK\|CLEAR_TASK` | 部分（常驻推送进程可能存活） | 是 | ~90-95% | manifest 加 `KILL_BACKGROUND_PROCESSES`（normal 权限，装机即授予） |
| P2 | 仅 `NEW_TASK\|CLEAR_TASK` | 否 | 是 | ~85% | 无 |
| P3 | 现状 `NEW_TASK` | 否 | 否 | ~50%（当前 84% 失败的来源） | 无 |

**P0 不再与 P1 同时发起。** 挑刺已指出：编排器是单 PC 串行 adb + logcat 轮询，force-stop 的实际到达时间是数秒到数十秒，完全可能落在 Agent 已经冷启、甚至已进编辑器之后——把填好正文的发布页直接杀掉，而 `TaskCoordinator.kt:15-18` 的 `reachedEditor` 闸门此时禁用自愈，只能转人工。改为：

- 信号带 nonce 与截止时间：`Log.i("AgentSwitch", "restart_douyin:<task_id>:<epoch_ms>")`
- 编排器丢弃时间戳超过 **3s** 的过期信号并计数（`tools/agent_orchestrator.py` 的 `watch()`）
- Agent 在 `normalizeDone` 后作废该 nonce；即便迟到的 force-stop 落下来，也只表现为一次 `APP_NOT_FOREGROUND`（可检测、可重试），不会静默毁掉编辑进度
- 保留"同一台机 20s restart 冷却"防 logcat 抖动

**归一化序列**（跑在独立 Thread，绝不放 a11y 回调线程，照抄 `fillAndPublish` 的 `Thread{}` 模式）：

```
0. Selectors.usePlatform(目标平台)          ← 必须第一行，见下方"全局 Selectors 陷阱"
1. 廉价 recognize()：HOME 且无阻断页 → 直接 return normalizeDone
2. 置 normalizing = true（AtomicBoolean）    ← 见下方"与 4s tick 互斥"
3. Log.i("AgentSwitch","restart_douyin:<id>:<ts>")
4. startActivity(MainActivity, NEW_TASK|REORDER_TO_FRONT)，sleep 500ms
   （不能省：killBackgroundProcesses 只杀后台进程）
5. killBackgroundProcesses(pkg)，sleep 800ms
6. launchIntent.addFlags(NEW_TASK|CLEAR_TASK|NO_ANIMATION) → startActivity
7. 800ms 轮询验证循环（不依赖 4s tick）
finally { normalizing = false }              ← 异常/超时都必须复位
```

**归一化完成判据（四条全满足）**
1. `actions.root()?.packageName == 目标包`
2. `recognize() == HOME`（沿用现有已验证判据：`首页`+`我` 且 `消息|朋友|拍摄按钮`）
3. 无任何阻断页命中（SPLASH_AD / APP_FIRST_RUN_DIALOG / UPDATE_DIALOG / TEENAGER_MODE / LOGIN_REQUIRED / SECURITY_CHALLENGE / LIVE_ROOM / COMMENT_SHEET / SYSTEM_DIALOG）
4. **间隔 ≥1.5s 的两次采样都满足**（冷启会经过 splash→feed 的中间帧，单次采样会误判）

**超时预算**：L1 = 45s，L2 = 60s，单任务最多两次（L1 失败升 L2），最坏 105s，远小于 lease 300s。每次打一行结构化日志 `normalize level=L1 ok=true elapsed=12.4s splash=1 firstrun=0 popup=0`，用它反过来校准预算。

**三个必须处理的实现陷阱**

| 陷阱 | 说明 | 处置 |
|---|---|---|
| **与 4s tick 互斥** | 归一化跑在独立 Thread，而 `reevaluate()` 仍每 4 秒把当前页面当任务步骤驱动；现有自愈词表恰好含「跳过」，正好会去点开屏广告 | `normalizing` 置真期间 `reevaluate()` 直接 return，a11y 回调只服务归一化自己的 800ms 轮询；`finally` 块保证复位，否则整台机永久不响应页面事件 |
| **全局 Selectors** | `Selectors.current` 是进程级 `@Volatile`，只在 `TaskCoordinator.kt:38` 与 `AgentForegroundService.kt:969`（终态回传**成功后**）设置。上一条 XHS 任务终态回传失败时，current 会停在 XHS 配置上，随后抖音归一化拿 XHS 的 `homeTabsPrimary` 判首页 → 永远不满足 → 45s/60s 全部走完后 `NORMALIZE_TIMEOUT` → 自动重试 → 同样结果 | AppNormalizer 第一行强制 `usePlatform(目标平台)`；`runBroadcast` 入口显式 `usePlatform("douyin")`；终态回传**失败路径也要复位** Selectors；归一化日志打出所用 selector 平台标识 |
| **开屏广告全屏热区** | 整屏都是跳转热区，误点会跳去第三方 App 或应用商店 | SPLASH_AD 提升为 `recognize()` 的**全局优先级**（不只在归一化阶段判）；`TaskCoordinator` 自愈分支最前面加前置：命中 SPLASH_AD 直接 return 等待，不进 dismiss 词表、不按 BACK；**把「跳过」从通用 `RECOVERY_DISMISS_LABELS` 里移除**，只在 SPLASH_AD 分支以精确文本 + 计数上限（≤2 次）使用 |

**同时必须从 `RECOVERY_DISMISS_LABELS` 删掉「退出」「坚持退出」「返回」**——这三个词会把抖音关掉，是现存的隐性自伤。

### 2.3 新增页面识别清单（8 页 → 18 页）

`recognize(root, pkg, platform)` 新签名。优先级（覆盖页必须排在 HOME 之前）：

```
NOT_IN_APP > SECURITY_CHALLENGE > LOGIN_REQUIRED > TEENAGER_LOCKED > TEENAGER_MODE
> SYSTEM_DIALOG > APP_FIRST_RUN_DIALOG > UPDATE_DIALOG > SPLASH_AD
> PUBLISH_CONFIRM > PUBLISH_SUCCESS > PUBLISH_REJECTED
> TEXT_TEMPLATE > TEXT_COMPOSER > MEDIA_PICKER > COMMENT_SHEET > LIVE_ROOM
> PUBLISH_ENTRY > HOME > UNKNOWN
```

| 新页面 | 判据（**一律 ≥2 个标记词**） | 处置 | 可重试 |
|---|---|---|---|
| **APP_FIRST_RUN_DIALOG**（新增，挑刺发现的缺口） | 同包 + 命中（`同意`\|`继续`\|`知道了`\|`去开启`\|`暂不`\|`以后再说`）+ 底部 tab 不可见 | **只点否定项**（暂不/以后再说/不允许/取消），绝不点同意类 | 是 |
| NOT_IN_APP | `root.packageName != 目标包`（含 null）。只能在 `reevaluate()` 主动轮询里判 | 归一化阶段→重发 restart 信号 + 自己 CLEAR_TASK（≤2 次）；已进编辑器→转人工 | 是 |
| SPLASH_AD | `跳过` + 同屏（`广告`\|`点击查看详情`\|`滑动查看`\|desc 匹配 `跳过\s*\d`） | 只等待；6s 后 `tapExact("跳过")`，≤2 次。禁用一切坐标点击与 BACK | 是 |
| TEENAGER_MODE | `青少年模式` + （`我知道了`\|`每日使用时长`\|`时间锁`），且**不含**`输入密码` | 精确点「我知道了」≤2 次；**绝不点「开启青少年模式」** | 是 |
| TEENAGER_LOCKED | `青少年模式` + （`输入密码`\|`验证密码`\|`忘记密码`\|`退出青少年模式`） | failed(TEENAGER_LOCKED) + 告警；**关 auto_publish 需连续 2 次命中** | 否 |
| LOGIN_REQUIRED | **≥2 个标记词** 且 **底部 tab（首页/我）不可见**。词表复用 `DouyinAccessibilityService.kt:112-116` 已验证的：立即登录/一键登录/手机号登录/登录抖音/验证码登录/其他方式登录/登录后 | 上报 `logged_in=false` + failed(LOGIN_REQUIRED) + 告警；**关 auto_publish 需连续 2 次命中** | 否 |
| LIVE_ROOM | **仅 douyin 生效**，需 2 个标记：（`说点什么`\|`发个弹幕`）+（`送礼物`\|`在线`\|`榜一`\|`关注主播`） | back()，仍在则点右上「关闭」/X，≤3 次 | 是 |
| COMMENT_SHEET | `条评论` 或（`写评论`\|`善语结善缘`）且底部 tab 不可见 | back() 收起 | 是 |
| UPDATE_DIALOG | `发现新版本`\|`立即更新`\|`版本更新`\|`检测到新版本` | 精确点「以后再说/稍后再说/暂不更新/取消」≤2 次 | 是 |
| SYSTEM_DIALOG | pkg ∈ permissioncontroller/systemui/packageinstaller | **只点「禁止/拒绝/取消/不允许」**（录屏授权白名单除外），点不到就 BACK | 是 |
| PUBLISH_REJECTED | 处于发布流程内 + （`发布失败`\|`内容涉嫌违规`\|`重新编辑`\|`审核未通过`） | failed(CONTENT_REJECTED) + 内容置 `needs_review`（**不退回池**，否则毒药内容会被别的账号再取再驳） | 否 |

**四条纪律**

1. **`LOGIN_REQUIRED` 绝不允许单条「登录」精确文本命中。** `PageRecognizer.kt:74` 的 `containsAny` 是对全屏所有节点做 `text.contains()` 的**子串匹配**，信息流里任意一条含「登录」二字的内容都能把正常账号打成未登录并永久停掉自动发布。必须新增 `exactText()` helper（比较 `node.text` 全等）。
2. **影子模式 3 天必须覆盖全部 10 条新判据**，尤其是 4 条带"关 auto_publish"权力的（LOGIN_REQUIRED / TEENAGER_LOCKED / SECURITY_CHALLENGE / PUBLISH_REJECTED）。只记日志 `shadow_page=LIVE_ROOM`，不做处置。
3. **上线前必须实机取样**：在 1 台云机上 force-stop + 冷启 **20 次**，逐次 dump 页面，把真实出现的首启弹窗序列（隐私政策更新/A13 通知权限说明/定位权限前置/个性化推荐开关/继续使用引导）录进词表。不做这一步，全矩阵会以 `NORMALIZE_TIMEOUT` 停摆——这些弹窗与目标 App 同包，既不是 SYSTEM_DIALOG 也不在原方案的 9 页里。
4. 新词表全部进 `SelectorConfig`（新增 key），走后端 `selectors.json` 热更——抖音改文案不用重刷 37 台。

### 2.4 结构化 error_code

`AgentStatusUpdate` 加 `error_code: str | None`；`PublishTask` 加 `error_code VARCHAR(32)`。**唯一真源放在 `backend/app/core/enums.py`，severity 也放在同一张表里**（通知方案不得再维护第二张 event→severity 表，见 §3.2 的裁决）。

**RETRY（环境类，自动重试，不进 waiting_confirmation）**
`NORMALIZE_TIMEOUT` / `APP_NOT_FOREGROUND` / `LAUNCH_FAILED` / `UNKNOWN_PAGE`（`reachedEditor=false`）/ `PAGE_STALL` / `LEASE_EXPIRED_EARLY` / `AGENT_RESTARTED`

**NEVER_RETRY（人/账号类，终态或人工窗口，绝不自动重试）**
`SECURITY_CHALLENGE` / `ACCOUNT_ABNORMAL` / `LOGIN_REQUIRED` / `TEENAGER_LOCKED` / `CONTENT_REJECTED` / `PUBLISH_UNCERTAIN` / `GROUP_PARTIAL_SENT` / `A11Y_UNBOUND` / `UNKNOWN_PAGE_AFTER_EDITOR` / `CONTENT_TAKEN` / `QUOTA_EXHAUSTED`

**`LEASE_EXPIRED` 不能是单一可重试码——这是真正的重复发帖路径。** `TaskCoordinator.kt:355` 在点击「发作品/发布笔记」**之前**就上报 `current_step="publishing"`、`progress=98`。Agent 在点击之后、结果识别之前挂掉（App 被杀 / 无障碍掉线 / 手机重启），租约 300s 后过期 → 判 FAILED → 若按 RETRY 重投，同一条内容在真账号上发第二遍。而 `PUBLISH_UNCERTAIN` 这个安全闸完全绕不到这条路上，因为它需要 Agent 活着才能上报。

```python
# reclaim_expired_tasks 写 error_code 时必须分流
POST_PUBLISH_STEPS = {"publishing", "verifying_result"}
if task.current_step in POST_PUBLISH_STEPS or (task.progress or 0) >= 95:
    code = ErrorCode.PUBLISH_UNCERTAIN     # NEVER_RETRY，内容置 needs_review
else:
    code = ErrorCode.LEASE_EXPIRED_EARLY   # RETRY
```

**`error_code IS NULL` → 一律不自动重试。** 后端先上线、37 台 APK 逐台刷（16 台 LAN 直连、其余走 adb、还要遵守 A13 刷机纪律），中间必然有数天新旧 Agent 并存。宁可不修也不能乱重试（旧机没有归一化，重试必然再失败，纯浪费产能还会触发 device_failstreak）。心跳增加 `agent_version` 上报，设备卡与告警 payload 都带版本号；"全部升到 vX 后才允许把 NULL 改判"做成显式的 AppSetting 开关，不靠人记得。

### 2.5 重试策略

**参数表**

| 参数 | 值 | 依据 |
|---|---|---|
| `retry_max_attempts` | 3（首发 + 2 次自动重试） | 84% 的失败是"不在一级页面"，归一化后一次重试就该成功；3 次以上是环境/账号问题 |
| 退避 | `180s → 600s`，各带 ±25% jitter | 3 分钟够云机收干净上次的进程和网络；10 分钟覆盖盒子短时抖动；jitter 防 37 台同波峰 |
| 归一化等级 | attempt1→L1(45s)；attempt2→L2(60s，优先 adb force-stop，冷启后先去「我」页校验登录态) | 逐级升强度 |
| attempt3 | **降级 `manual_confirm`，且窗口独立缩短到 120s，超时判 cancelled 不判 failed** | 见下方裁决 |
| `device_daily_retry_cap` | 6 次/机/天（CN 时区 0 点重置） | 止损闸 |
| `content_max_auto_retry` | 4 | 防内容级死循环 |
| 冷启抖动 | ±30% | 防 37 台同波峰形成规律行为特征 |

**attempt3 的裁决**：原方案"第 3 次强制 manual_confirm"与"把设备从人工窗口解放出来"互相抵消——它必定停在发布页占满 300s，按日预算 6 次算单机每天多出 30 分钟纯等待。改为：**独立 120s 短窗口 + 超时判 cancelled（内容退回池、不计 `auto_retry_count`）**，且**仅当该账号所属城市存在 enabled 的 NotifyRoute 且当前不在静默时段时才降级 manual_confirm**，否则直接判失败释放设备——没人能收到通知就不要留窗口。

**六道防死循环闸**（计数存**后端 PublishTask 行**，不存 Agent——Agent 侧任何计数在杀进程/掉线/重装后就没了）

1. `attempt >= max_attempts` 硬停
2. `root_task_id` 链上 attempt 累计计入上限——人工「重发」也继承链，避免人工 × 自动相乘
3. `error_code ∈ NEVER_RETRY` 根本不进重试队列
4. **内容级闸**：`ContentItem.auto_retry_count > 4` 时不退回池，置 `needs_review` 并告警（否则"失败→回池→被另一账号取走→再失败"可以绕过任务级计数无限循环）
5. 设备级日预算 6 次，超了暂停该设备 auto_publish + `health_message` + 告警
6. 重试只由后端一个 sweep 创建，条件 `status=failed AND next_retry_at<=now AND attempt<max_attempts`，创建后立即清空 `next_retry_at`（幂等）

**新增的第七、第八道闸（挑刺补）**

7. **内容预留态，防跨账号重复发布。** 现状 `_finalize_content`（`tasks.py:107-140`，已核对）在任务失败那一刻就把 ContentItem 退回 PENDING，而重试要 180s 后才创建；这个窗口里 `maybe_generate_auto_task` / `schedule_posts` 可以把同一条内容派给别的账号。`retry_task` 只在 content.status ∈ {PENDING, PUBLISHING} 时才重新加锁（`tasks.py:364-373`），若已变 PUBLISHED 就静默跳过加锁，但重试任务的正文早已拷贝在任务行上，照样会发出去。
   → 修法：任务失败且 `next_retry_at` 非空时，`_finalize_content` **不退回池**（保持 PUBLISHING 或新增 RESERVED 态）；只有整条 `root_task_id` 链终结（attempt 达上限或命中 NEVER_RETRY）才退回。sweep 创建重试任务前**必须重查** `content.status`，非 {PENDING, RESERVED} 一律放弃并写 `error_code=CONTENT_TAKEN`。
8. **配额闸。** `count_today_published` 只数 SUCCEEDED（已核对，`tasks.py:545-550` 一带），`_count_day_committed` 只数带 `scheduled_at` 的任务，而 sweep 新建的重试任务 `scheduled_at=None`、`claim_next_task` 不做配额校验——一条重试成功 = 当天第 3 篇，`daily_quota=2` 被静默突破。
   → 修法：sweep 创建前复用与 `maybe_generate_auto_task` 相同的配额判定；更稳的做法是给 `PublishTask` 加 `is_retry`，配额统计时同一 `root_task_id` 链只计 1 次。

### 2.6 状态机（文字描述）

```
queued ──claim──> leased ──agent上报──> running
                                         │
        ┌────────────────────────────────┼────────────────────────────┐
        │                                │                            │
   环境类失败                      人工类阻断                    正常完成
   (RETRY 码)                   (NEVER_RETRY 码)                      │
        │                                │                            ▼
        ▼                                ▼                        succeeded
   failed + next_retry_at        waiting_confirmation           (内容 PUBLISHED)
   内容保持 RESERVED             (waiting_since=now)
   设备立即释放                   + 按城市推企微/邮箱
        │                         + 5 分钟窗口
        │                                │
        │              ┌─────────────────┼──────────────────┐
        │           人来了            5 分钟无人           安全类
        │              │                 │                  │
        │              ▼                 ▼                  ▼
        │          succeeded      MEDIA_PICKER/          failed
        │          /cancelled     UNKNOWN(编辑器后)      不重试
        │                         → 重试(L2)             关该账号 auto_publish
        │                                                 (需连续2次命中)
        ▼
  sweep(60s) 六+二道闸校验 ──通过──> 新建 queued (attempt+1, root_task_id 继承)
        │                                                    │
        └──不通过──> failed 终态                    attempt3 → manual_confirm
                     内容退回池 / needs_review              (120s 短窗口)
```

**三个终点的语义**：`succeeded`=已发出；`failed(NEVER_RETRY)`=人的问题，等人；`failed(链终结)`=内容退回池给别的账号，或超过 4 次后置 `needs_review` 不再入池。

### 2.7 群发与回采

**群发：要归一化，同一 L1。** `runBroadcast` 现在也是只加 NEW_TASK 拉起（`AgentForegroundService.kt:753-757` 一带），吃同一份亏。冷启后仍要保留 `pullToRefresh`（冷启先显示旧缓存列表）。

**群发的 sent 计数必须增量上报，不能等终态。** 原方案的 `sent==0 才自动重试` 依赖一个在最需要它的时候一定拿不到的计数——群发失败最常见的成因恰恰是崩溃/掉线/租约超时，此时 Agent 根本没机会上报终态 sent。
→ 每成功发出一个群就立即 PATCH 一次任务行（复用现有 status 上报通道加 `sent` 字段）；后端把 **`sent IS NULL` 一律视同 sent>0**（不可重试，报 `GROUP_PARTIAL_SENT` 转人工）。宁可漏重试也不能重复群发。

**回采：不做杀进程归一化，只接入阻断页识别。** `collectDouyinMetrics` 已有 36 步状态容忍走查（`AgentForegroundService.kt:477-520`），本来就不假设起始页；冷启反而多吃一次开屏广告。真正要补的是：现在回采撞到青少年模式/登录页会**静默返回 0 条**（"未回采到内容数据"），这是"回采数据为 0"的一类真因——接上新页面识别后命中 LOGIN_REQUIRED/TEENAGER_LOCKED 就上报/告警，而不是空手而归。

### 2.8 人工窗口（5 分钟）

**先重试，人工窗口只留给"人能解决、且机器不该碰"的三类。**

- **环境类**：Agent 直接报 `failed + error_code`，**根本不进 waiting_confirmation**。仅此一改就能清掉现在 42 条 confirmation_timeout 的大半。
- **人工类**：进 waiting_confirmation + 立刻按城市路由推送 + 5 分钟窗口（`confirmation_timeout_seconds` 600→300，与 B3 同 commit）。

5 分钟超时后**按 error_code 分派，不是统一重试**（这是对"超时直接重试"这条决定的唯一例外，见 §9-Q2）：

| error_code | 超时后 |
|---|---|
| `MEDIA_PICKER` / `UNKNOWN_PAGE_AFTER_EDITOR` | 重试任务，走 L2 |
| `SECURITY_CHALLENGE` / `LOGIN_REQUIRED` / `ACCOUNT_ABNORMAL` / `TEENAGER_LOCKED` | 判 failed，不重试，升级告警；关 auto_publish 需连续 2 次命中 |
| `PUBLISH_UNCERTAIN` | 判 failed，内容置 `needs_review`（人工去 App 里确认到底发出去没有），**永不重试** |

**`SECURITY_CHALLENGE` 首次只暂停该账号当天剩余排期，不永久关 auto_publish**；同城 1 小时内 ≥3 台命中则全局把归一化降级回 P2/P3（不杀进程）并告警，避免越试越猛。

## 3. 转人工通知

### 3.1 地基：两张表 + 两条 loop + 一条派生告警

`backend/app/api/v1/routes/alerts.py:27-34` 是纯派生只读，每次 GET 全表重算，没有任何已发送状态。把外发挂在它上面，一台设备掉线 30 分钟 = 前端轮询 120 次 = 120 条重复消息，必然撞 45009。

**表 1：`NotifyRoute`**（城市 → 收件渠道）
`city`（具体城市 / `*` 兜底 / `__global__` 系统级）、`channel`(wecom|email)、`target`、`oncall_mobiles`、`min_severity`、`quiet_hours`、`daily_cap`、`attach_screenshot`(bool, **默认 false**)、`enabled`、`consecutive_failures`、`last_error`；唯一约束 `(city, channel)`。

**表 2：`AlertDispatch`**（发送台账 = 去重 + 重试 + 审计）
`dedup_key`(UNIQUE)、`event`、`severity`、`city`、`device_id`、`account_id`、`task_id`、`root_task_id`、`screenshot_id`、`payload_json`、`route_id`、`channel`、`fallback_from`、`status`(pending|sent|failed|no_route|suppressed|aggregated)、`attempts`、`next_retry_at`、`last_error`(已脱敏)、`created_at`、`sent_at`、`resolved_at`、`resolved_by`。

**两条 loop**：`_notify_dispatch_loop`（15s）+ `_notify_periodic_loop`（5min）。

**核心分工（不能破）**：业务代码只调 `notify.enqueue(...)`，它做去重判断后写一行 pending 就返回，**永远不发 HTTP**。

> **`enqueue` 必须开自己的 Session、自己的事务，整段 try/except 吞掉一切异常。**（blocker）`update_agent_status` 跑在 Agent 的 HTTP 请求线程里；若 enqueue 在同一 session 里插入 AlertDispatch 撞上 `dedup_key` 的 IntegrityError，SQLAlchemy 会把整个 session 置为 rollback-only，Agent 的终态写入随之失败。而 `AgentForegroundService.kt:952-979` 对 `updateStatus` 异常只写一行本地状态、不重试，`TaskCoordinator.kt:105-110` 的 `resultReported` 是一次性闩锁——于是任务永远停在 running、永远续租、永不过期、这台机永不领新任务。**等于通知系统的一个唯一约束获得了停掉一台设备的能力。**
> 配套单测：monkeypatch 让 `enqueue` 无条件抛异常，断言 `update_agent_status` 仍把任务写到终态。同时补上 Agent 侧 `updateStatus` 的失败退避重试（≥3 次），这是现存的独立缺陷，通知会显著放大它。

**一条派生告警 `notify_broken`（P0 级重要，纯 alerts.py 改动，零新表）**
通知系统自己坏了的时候，唯一能被看见的面只有控制台铃铛（它不依赖外发通道）。数据源：`NotifyRoute.enabled=false`、或 `consecutive_failures>=5`、或近 24h `AlertDispatch` 中 `status ∈ {no_route, failed}` 计数 > 0。severity=critical。这条完全符合 `alerts.py` 现有的纯派生只读定位，但能保证"外发挂了"一定出现在红点上——否则首次上线时 SMTP 大概率还没配，`route_broken` 的兜底通道本身就不存在，系统静默失明。

### 3.3 城市路由

**城市真源是 `DeviceAccount.city`**（`entities.py:89`）。`Device.city` 是 legacy 字段，序列化时会被 primary douyin 账号覆盖（`devices.py:256`）。`PublishTask` 没有 city 字段，task 类事件必须走 `device_id` 反查——**这一步在 `enqueue` 时就做完并写进 `AlertDispatch.city`，不要留到发送时再查**（那时设备可能已被改过城市）。

**查找与回退**：城市事件 `city 精确 → "*" → 无`；全局事件 `"__global__" → "*" → 无`。
`min_severity` 过滤（配 P2 = 只收 P1+P2）；`quiet_hours` 命中时 P2/P3 转 `suppressed` 进次日汇总，**P1 无视静默时段**。

**没配城市的三层兜底，一条都不丢**
1. `未分组` 是合法城市 key，可以直接给它配路由（云机6011 落在这里，但正确做法是补真实城市）
2. 配一条 `city="*"` 的兜底路由 —— 部署 checklist 必做项
3. 都没有 → 落 `status="no_route"`，**不丢弃**。控制台顶部常驻红条：`3 条告警无收件人（城市：杭州、未分组），点此补配路由`；`GET /health` 在 enabled 路由数为 0 时返回 `notify_unconfigured:true`

**权限**：`require_admin_role`（管理员，不是 operator）。webhook key 没有签名、没有 IP 白名单，拿到 key 就能往运营群发任意消息。

**落地顺序写死：先跑城市清洗脚本 → 再建 NotifyRoute。** 若路由先配好、清洗后跑，清洗后的 `DeviceAccount.city` 与路由表 city 会失配，而失配的表现是"告警静静躺在 no_route 里"——最难被发现的失败模式。`NotifyRoute.city` 写入走同一个 `normalizeTag`（前后端各一次）。

### 3.6 降噪（五层，从内到外）

**① dedup_key（UNIQUE 索引）** —— 数据库唯一约束就是幂等实现。持续状态类的键必须带"起点时间桶"（`offline:{device_id}:{起点 epoch//60}`），同一次掉线永远同一个键。

**② 静默期（per event × per target）**

| 事件 | 静默期 |
|---|---|
| `human_security` / `retry_exhausted` | 0（每次都是新任务） |
| `device_offline` | 60 min |
| `a11y_unbound` | 30 min |
| `device_failstreak` | 2 h |
| `account_health` / `content_pool_critical` | 6 h |
| `content_pool_low` / `account_logout` | 24 h |

**③ 聚合窗口 60 秒** —— 按 `(route_id, city, event, severity)` 分组，同组 ≥2 条**且 severity != P1** 时合并。**P1 的例外**：同一 event 在 60 秒窗口内 ≥3 条时也合并为一条「N 台设备…」并只 @ 一次，正文逐行列出设备名（样例 E2）——这与"不漏掉某台机"不冲突。

**④ 令牌桶 18 次/分钟（per webhook route）** —— **计的是 HTTP POST 次数，不是告警条数**。一条带截图的告警消耗 2 个令牌，聚合消息不发图因此消耗 1 个（这正是聚合设计的收益之一）。桶上限 18 等价于极端情况下 9 条带图告警/分钟。官方上限 20/分钟，留 2 条给测试发送。撞 `errcode 45009` **不重试、不计 attempts**，直接 `next_retry_at = now + 60s`。**按 severity 拆成两个独立桶，P1 独占其中一个**，P2/P3 抢不走。

**⑤ 城市熔断 + 每日上限**
- 同一路由 10 分钟内已发 >6 条 → 30 分钟熔断，期间 P2/P3 只落台账；熔断开始时群里发**一条**告知，末尾发一封合并邮件。**P1 不受熔断影响**——熔断的意义是保住 P1 的送达。
- `route.daily_cap`（默认 30）只统计 P2/P3。P1 单独硬顶 20 条/天，超了发一条「矩阵大面积异常，请立即检查」并停止逐条外发。

### 3.7 失败与重试

```
enqueue → pending ──成功──> sent ──人工处理──> resolved_at + resolved_by
             ├─45009 频率超限 → pending, +60s, attempts 不+1
             ├─网络/5xx      → pending, attempts+1, 退避 30s/2min/10min
             ├─attempts 达 3 → 切 email 路由（fallback_from="wecom", attempts 归零）
             ├─93000 类（机器人被移除/群解散）→ failed + 立即禁用该路由 + route_broken
             ├─无路由 → no_route（可复活，不是终态）
             └─被静默/被聚合 → suppressed / aggregated
```

- **必须解析 body 的 `errcode`**：企微业务错误也返回 HTTP 200，只看 status_code 会静默丢消息
- 超期丢弃：pending 超 6 小时的 P2/P3 标 failed（原因 `stale`）；**P1 不丢弃**
- **闭环只统计人工写操作**（confirm / cancel / retry / 更新账号）。系统自动重试走完的标 `auto_resolved` 单独计数——否则"已闭环"会虚高到接近 100%，掩盖"通知根本没人看"这个真问题。控制台铃铛条目加「标记已处理」动作，按 device_id/task_id 匹配活跃 AlertDispatch 写 `resolved_at`
- **webhook key 与 SMTP 密码走 `config.py:56` 已有的 `_resolve_secret` 机制**，存 storage 下独立文件，DB 只存引用/别名。理由：生产是一台笔记本，`storage` 目录已放着 `.admin_token`，且已经做过一次「整包迁移到第二台 PC」——那次迁移会把 `agent.db` 原样拷走。迁移打包脚本白名单排除这些文件；migration-package 的 checklist 加一条「换机后必须重建企微机器人」
- 异常脱敏：`_MASK = re.compile(r"(key=)[A-Za-z0-9_-]{8,}")`，`last_error` / `append_log` 全部写脱敏后的字符串。提交前 grep 检查要把 `.db` 和 `storage` 目录纳入扫描范围
- API 响应一律脱敏回显 `...key=***c4f2`，编辑时"留空=不改"

### 4.3 规则清单 R0–R14

处置四种：`drop`（落 `auto_rejected`，可翻看可恢复）/ `fix`（自动修，记 patch 可撤销）/ `regen`（单字段局部重生成，1次）/ `human`。

**L0 结构层（hard，全 drop，不消耗人工）**

| id | 判据 | 处置 |
|---|---|---|
| R0 | `drafts` 非 list 或条目非 dict | 整批 drop（现有 `content_engine.py:329` 已做） |
| R1 | `body.strip()` 为空 | **drop**。当前漏洞：空 body → `_similar` 返回 0.0 → dup=0 → pending，一条空正文能一路走进内容库（`accept_draft` 直接构造 ORM，绕过 `ContentCreate` 的 `min_length=1`） |
| R2 | `cover_title.strip()` 为空 | drop |
| R3 | body 含控制字符 / 以「，、（」结尾（明显截断） | human |

**L1 数值层**

| id | 判据 | 阈值 | 档 | 处置 |
|---|---|---|---|---|
| R4 | 封面字数 `len(re.sub(r'\s','',s))` | >50 | soft | ≤60：`human`+标黄；>60：`regen`（只重写封面） |
| R5 | 标题字数 | >20 | soft | `human`+标黄（不自动截断，会切半句） |
| R6 | 正文字数 | >100 | **soft，首月不参与自动拒** | ≤150：仅标注；>150：`human`。理由见前提2 |
| R7 | topics 数量 | >5 | fix | 截到前 5 个 |
| R8 | topics 数量 | <3 | soft | `human`（不能凭空造话题） |
| R9 | topics 含 `#`/空白/重复 | — | fix | 全局去 `#`、去空格、去重（现在 `content_engine.py:355` 只去前缀） |

**L2 词表层**

| id | 判据 | 处置 |
|---|---|---|
| **R10-solo** | 命中 `底裤/接盘侠/入国军/踩盘` | **hard → drop**（这四个词没有中性用法） |
| **R10-ctx** | 命中 `崩了/没救了/腰斩/暴雷` 后看**左窗口 8 字**：命中白名单正则→不算；窗口内出现标的词（房价/楼市/学区房…）→ **soft → human**；都不满足→不算 | 最高只能到 human。校准目标：在历史 168 条上命中数从裸匹配的 6 条降到 **0–1 条** |
| **R11** | 只在**正文末 30 字**内匹配结尾套话（不能全文匹配——正文中段的自然提问是好东西） | `fix`：按 `。！？\n` 切句删掉最后一个命中的整句；删完 <20 字则回滚为 `human`。patch 进 review_json 可一键撤销 |
| **R12** | 手机号 `1[3-9]\d{9}`、微信号 `(微信\|vx\|v信\|wx)[:：\s]*[A-Za-z0-9_-]{5,}`、外链 `https?://`、`@某某` | **hard → human**（不 drop，可能是引用）。这类一旦发出去是账号级风险，比长度超标严重一个量级 |

### 4.4 无法确定性判定的部分：LLM judge

| 提示词条款 | 能确定性判吗 | 处置 |
|---|---|---|
| 严禁虚构夸大承诺 | **部分**（"包涨/必赚/稳赚/一定翻倍/闭眼买"可入词表；"这个板块明年就起来了"必须语义） | 词表兜 30%，其余交 judge |
| 像活人发的碎碎念 | 不能 | judge |
| 换角度而非改写同一篇 | 不能（查重抓字面，抓不到"同一观点换个说法"） | judge |
| 数字可信度 | 不能 | judge 标"存在未经核实的数字"，不判真假 |
| 城市判定是否正确 | **词表抽取比 LLM 强** | **不交 judge**，见 §4.5 |

**唯一定位：judge 只能把 `pass` 降级成 `human`，永远不能把规则命中的东西改判成通过，也不能 drop。** 这条性质决定了 judge 不稳定的最坏后果是"多送几条给人工"而不是"漏放垃圾内容"。

**判定 prompt（照抄可用）**

```
system:
你是内容合规校验器。只做判断，不改写、不建议、不解释多余的话。
对每篇文案，逐条回答下面 4 个问题，每条只能答 yes / no / unsure：

Q1 虚构或夸大承诺：是否出现对未来收益、涨跌、结果的确定性保证
   （如"肯定涨""稳赚""必然翻倍""闭眼买"）？
   注意：转述他人观点、提出疑问、表达个人担忧 → no。
Q2 机器腔：是否读起来像营销稿/AI 稿而非真人碎碎念
   （通篇书面语、无具体细节、无个人经历、排比堆砌）？
Q3 未经核实的具体数字：是否给出了具体百分比/成交量/价格数据且没有说明来源？
Q4 与给定的参考文案是同一观点的换皮改写（不是新角度）？

输出严格 JSON：
{"results":[{"i":0,"Q1":"no","Q2":"yes","Q3":"no","Q4":"no",
  "quotes":{"Q2":"原文中支撑该判断的连续片段，必须逐字来自正文"}}]}
凡答 yes 的问题，必须在 quotes 里给出原文连续片段。给不出就答 unsure。
```

**五道防线（缺一不可）**

1. **`temperature=0`**（现在生成用 1.0，`deepseek.py:50` 默认；judge 必须单独传 0）
2. **quote 必须是原文子串**：逐条校验 `quote in norm(body)`，不是子串就把该 yes 作废降为 unsure。纯代码校验、零成本，是压制幻觉最有效的一招
3. **结果落库缓存**：新表 `ReviewJudgeCache`，主键 `sha256(norm(body) + rules_version + review_model)`。**必须先修 model 字段 bug**——草稿落库写的是 `settings.deepseek_model`（env），实际调用用 `resolve_model(session)`（`content_engine.py:325` vs `:340`），管理员换过模型后草稿卡显示的模型名和成本记账都是错的，缓存会串
4. **judge 单独配 `review_model`，不与生成共用。** 生成端和判定端共享同一套关于"什么话算承诺"的先验，Q1 恰恰是同质化盲区最深的一题
5. **fail-open 到 human**（blocker）：judge 包**独立的 30s 短超时**（不共用 generate 的 300s）+ try/except 全捕获。任何异常（超时/非法 JSON/额度耗尽/网关 5xx）一律降级 `needs_human`，并在 review_json 记 `{id:"L2_judge", hit:false, action:"unavailable"}`。**绝不允许 judge 的失败影响已生成草稿的落库**——那等于运营白花钱白等。generate 返回体带 `judge_ok` 标志，UI 显示「本批未经 AI 复核，请人工确认」

**成本不是约束，延迟才是。** 实测 72 条有记账的草稿：平均 246 prompt + 268 completion token，**单条 0.00078 元**，历史累计 0.056 元。judge 批量审 10 条约 **0.0044 元/批**（+56%，每千条 0.44 元）。但 generate 是同步阻塞（timeout 300s），**judge 必须整批一次调用**，10 条串行会把接口拖到不可用。

**稳定性验收改成**：同一批 10 条打乱顺序重判、并拆成两批 5 条重判，逐条结论一致率 ≥95%，且**必须绕过缓存跑**。原验收"连续判 3 次结论一致（由缓存保证）"测的是缓存命中，不是模型稳定性；真正的风险是"整批一次调用"引入的批次上下文依赖。

### 4.5 地域：不改写 city，只加 geo_hint

**实测的泄漏形态和直觉不一样**：95/95 条草稿的 city 全是「通用」（提示词里"判断目标城市"这条指令实际产出率 0%）；内容库 62 条通用内容里 **43–48 条正文点名了具体城市或区县**（上海 38、深圳 5，区县 静安4/奉贤3/金山3/浦东2/嘉定2/松江2/崇明2…）；`tasks.py:212-218` 的通用兜底让这批内容对全部 37 台机任意城市账号可领。dev 库已发布 49 条里实际跨城 0 起——**那是运气（深圳只有 5 台机、内容也大多是上海的），不是机制**。

**但原方案的 R13-c 会把内容池打穿。** 通用池从 62 掉到约 14-19 条，而北京 6 个账号在库里有 **0 条专属内容**、深圳只有 3 条；且 `_match_content` 的兜底只认 `GENERIC_CITIES = ["通用","全国",""]`，**「未分组」不在内**——18 台未分组设备（含有号的云机6011）完全依赖通用池。规则生效第二天这批账号取不到内容、自动发布静默停摆（不报错、不告警、不产生失败任务，在失败率指标上完全不可见）。

**裁决：改成双字段，不覆写 city。**

| 规则 | 判据 | 处置 |
|---|---|---|
| **R13-a** | 文本命中某城市线索词 | 写 `geo_hint=该城市`（**不改 city**）。命中多个不同城市 → `human`（可能是"上海和深圳哪个…"的对比文） |
| **R13-b** | `city` 已是具体城市但文本命中其他城市 | **hard → human**，不自动改 |
| **R13-c** | 同屏出现 **2 个以上同城线索**，或命中**带后缀形式**（"南山区"/"南山街道"） | 置 `geo_locked=true`。**只有 geo_locked=true 才排除跨城领取**，其余仍走通用池 |

**上线前必须先跑干跑模拟并断言**：按 R13 标记后，每个城市（含未分组走的通用池）可用量 ≥ 该城市账号数 × daily_quota × 2 天，不达标不许开。

**同时必须补一条现存的静默失败面**：`consume_content_into_task` 取不到内容时（`_match_content` 返回 None）现在完全静默——不建任务、不写日志、不告警。补一条日志 + 接入 `content_pool_critical`（§3.2 #12）。**这比地域泄漏更早会咬人。**

**词表三层**

| 层 | 内容 | 来源 | 维护成本 |
|---|---|---|---|
| L1 城市名 | 上海/北京/深圳… | **系统自生成**，复用 `GET /content/cities`（`content.py:101-114`） | 零 |
| L2 区县名 | 徐汇/浦东/南山/朝阳… | **民政部行政区划代码表**（公开 CSV，约 3200 条），写一次性脚本 `tools/import_geo_terms.py`，只取市→区县两级。**不要手打** | 一年一次 |
| L3 楼盘/商圈/地铁/学校 | 张江/前海/陆家嘴/深大 | 运营手工，UI 一个「地名词表」页 | 持续，但有反馈闭环 |

**维护闭环（词表能活下去的唯一原因）**：每条 `GeoTerm` 记 `hit_count` / `false_positive_count`，运营点「这条误报」时 +1；误报率 >30% 且命中数 ≥5 的词**自动置灰**并进管理员待确认列表。
**歧义词降噪**：南山/光明/朝阳/静安/宝安/福田加 `ambiguous` 标；单个歧义词单次命中 → soft 仅提示。

### 4.6 查重

**现状三个错误**

1. **取样错了，不是算法慢。** `_dup_corpus`（`content_engine.py:43-51`）两个 select 都是 `limit(400)` 且**没有 order_by**，SQLite 按 rowid 返回 → 拿到的是**最早的 400 条**。库到 900+ 时，最该防的"和上周刚发的撞车"恰恰漏掉。
2. **语料自我复制。** accepted 草稿的 body 与它生成的 ContentItem 完全相同，两边都进语料。实测 4000 组随机对里 19 组相似度 ≥0.90，**全部是这种自我复制**（jaccard=1.0）。
3. **只比 body。** 封面大字报和标题完全不参与——换个正文说法、复用同一句爆款封面，查重分照样很低。

**阈值：0.90/0.75 太高，中间是空档。** 实测随机对分布 **p50=0.09，p90=0.15，p99=0.26**，0.26 到 0.90 之间完全空档。

| 维度 | drop | human | pass |
|---|---|---|---|
| body | ≥0.85 | 0.55–0.85 | <0.55 |
| cover_title | 归一化完全相等 → human（不 drop，封面复用有时是有意的） | 3-gram Jaccard ≥0.80 → 提示 | — |

**时间窗加权**：近 30 天用上表，30 天以前的语料阈值各 +0.10。

**三步走**

- **第一步（10 行代码，80% 收益）**：去掉 `limit(400)` 无 order_by，改成 `order_by(created_at.desc()).limit(2000)`；ContentItem 排除 `status == "disabled"`；ContentDraft **排除条件用 `accepted_content_id IS NOT NULL` 而不是 `status != accepted`**（accept 后内容被删除或 accept 中途失败的草稿否则会永久退出语料，成为不会被发现的盲区）。
  实测 difflib 现在撑得住：正文平均 78 字，1 条 vs 2000 条 = **0.088s**，10 条一批 = **0.88s**。
- **第二步（正文变长后必须做）**：3-gram Jaccard 粗筛（1×2000 = **0.0073s**，快 12 倍，且对长度不敏感）→ top5 走 difflib 精算（<10ms）。指纹预存 `ContentFingerprint`，语料从此没有上限。
- **第三步：避雷语料。** rejected 草稿 + disabled 内容进一个**独立语料**，命中 ≥0.75 时不 drop，只在草稿卡标"这篇和你上次拒掉的 #X 很像"。现状 rejected 被排除在语料外（`content_engine.py:49`）= 系统不记得自己被否过什么，同一篇烂稿能反复生成占用人工时间；而前端方案要加的"批量退回=置 disabled"会叠加同一个病。

**阈值必须在生产库上重标。** 上述统计全部来自 dev 库（20 台设备、95 条草稿、73 条内容、0 条 publishtask），而 743 条任务 / 37 台云机来自生产机。W1 出口条件加一条：dev 与 prod 两份混淆表的误杀率差异 <10%，否则以 prod 为准。

### 4.7 三级流水线 + 内容池硬闸

```
生成返回 raw_drafts
   ↓
L0 结构校验 (R0-R3)             → drop（落 auto_rejected）
   ↓
L1 确定性规则 (R4-R14)          → drop | fix | regen(≤3次/批) | human
   ↓  只有"全过"或"仅 soft 命中"的进入
L2 LLM judge（整批一次，缓存优先，30s 超时，异常 fail-open）→ pass | human
   ↓                             ★不能 drop、不能翻案
L3 落库：
   auto_pass     → ContentItem(status=pending, source='ai_auto')
   needs_human   → ContentDraft(status=pending) + review_json
   auto_rejected → ContentDraft(status=auto_rejected) + review_json（可翻看可恢复）
```

**内容池硬闸（优先级高于运营的严格度滑块）** —— 三条路同时收窄供给（auto_reject 15-25%、R13 地域标记、`auto_retry_count>4` 不退回池），而没有任何一方在池见底时自动放宽。
→ 当某城市（含通用池）可用量 < 账号数 × daily_quota × **1 天** 时：自动把 `review.level` 降到 `loose`、暂停 auto_reject、暂停 `auto_retry_count` 的 needs_review 判定，写 `health_message` 并触发 `content_pool_critical`（P1 @人）。

**regen 边界**：只对单字段发一次极小请求（`max_tokens=800`），**每批 ≤3 次、每日 ≤50 次，按 token 维度记账**（不是全局维度）。

**generate 本身必须限流**（真正的口子，不是 regen）：单次最多 10 条、同步阻塞 300s、现在还要再串一次 judge，而 `/content` 全部路由 operator 令牌即可调。一个循环脚本就能同时占满额度和后端的同步请求槽——后端还必须单 worker（SQLite claim 互斥），generate 排队会直接拖垮设备的 claim 轮询。
→ 加 per-token 每日次数上限 + **全局互斥**（同一时刻只允许 1 个生成批次，第二个直接 429 而不是排队）。验收：并发调 5 次 generate，断言 4 次立即 429、claim 接口响应时间不受影响。

**顺带修的两个既有洞**（同一片代码，一起改成本最低）
- `accept_draft`（`content.py:426`）没有状态守卫，duplicate/rejected 的草稿能被直接 API 采纳进库——加一行 status 检查
- `model` / `cost` 记的是 env 而非 `resolve_model(session)`（`content_engine.py:325` vs `:340`）

### 4.8 比例目标与运营怎么调

现状基线：95 条草稿 → 采纳 68 / 拒绝 22 / 待审 5，**人工采纳率 71.6%**。

上线 4 周后目标：

| 档 | 目标 | 硬约束 |
|---|---|---|
| auto_rejected | 15–25% | **误杀率 <5%** |
| auto_pass | 40–55% | **误放行率 <5%** |
| needs_human | 25–40% | 人工日均处理量下降 ≥50% |

任一误差率破 5% → **自动回退到"全部转人工"并告警**（这条要真的实现成代码，不能只写在验收里）。

**「审核严格度」三档滑块**

| 参数 | 宽松 | 标准 | 严格 |
|---|---|---|---|
| 查重 drop/human | 0.92 / 0.70 | 0.85 / 0.55 | 0.78 / 0.45 |
| soft 规则处置 | 仅标注 | 标注，超限50%转人工 | 全部转人工 |
| judge unsure 归属 | pass | human | human |
| R6 正文超长 | 不参与 | >150 转人工 | >100 转人工 |

**滑块下面必须挂回放模拟器**——这是让运营敢动这条线的唯一办法。`POST /content/review/replay {level}` 拿最近 200 条历史草稿离线跑（LLM 走缓存，**不花一分钱、不发一次请求**）：

> 按"严格"档回放最近 200 条：自动通过 62 条(31%) / 转人工 88 条(44%) / 自动拒 50 条(25%)。
> 其中 **11 条你当初采纳过的会被自动拒**（点击查看）。

那句"11 条你当初采纳过的会被自动拒"就是决策依据。没有它，滑块是个盲盒，运营不会碰。

### 4.9 开关粒度与上线次序

**三层"与"关系，任何一层关掉即降级为全部转人工（安全默认）**
1. 全局总开关 `review.auto_enabled`（管理员）—— 关闭 = 规则照跑、结论照显示、**但不自动放行也不自动拒**。这就是影子模式。
2. 严格度档位（运营可调，配回放模拟器）
3. 按预设 `PromptPreset` 加 `review_enabled` / `review_level` 两列 —— 不同预设之间的质量方差远大于城市之间

**明确不做：按城市开关。** 95/95 条草稿的 city 全是「通用」，城市是运营在**采纳那一刻**才定的（`AIStudioView.tsx:590` 的本地 state，`DraftUpdate` 里根本没有 city 字段）。

**上线次序（不许跳步）**

| 周 | 动作 | 出口条件 |
|---|---|---|
| **W0** | **前置**：AIStudioView 状态 tab 化（待审/自动通过/自动拒/已拒绝/全部）+ `POST /drafts/{id}/restore` + 「这条误报」申诉 | 三类不可见草稿全部可见可恢复 |
| W1 | 规则引擎 + 影子模式（在**生产库**上跑），结论只显示不生效 | 跑满 200 条，产出规则结论 × 人工结论混淆表 |
| W2 | 按混淆表校准阈值（重点 R6 与查重）。修查重取样 + 语料自我复制 | auto_reject 候选的人工采纳率 <5% |
| W3 | 开 auto_reject（**只开 hard 档**：R0-R2、R10-solo、R12、R14 高分查重）。auto_pass 仍关 | 误杀申诉 <3 条/周 |
| W4+ | 视 W3 结果决定是否开 auto_pass（见 §9-Q4） | 抽检 50 条 auto_pass，硬性违规 0 条 |

> **W0 是硬前置。** 当前 `AIStudioView.tsx:75` 硬编码 `listDrafts('pending')`，duplicate/rejected 在 UI 里永远不可见。影子期采集到的人工结论天然缺失 auto_rejected 候选那一侧，而误杀率（规则拒 × 人工采纳）**恰恰只能从这一侧算出来**——不先做 W0，W2 的出口条件根本算不出来。

| 能力 | 做 | 说明 |
|---|---|---|

| 空态 | ✅ | 区分两种空 |
| 计数/徽标/图标 | ✅ | 现有能力平移 |

**明确不做（写进 `picker/index.ts` 顶部注释，防后人加戏）**：多选/tag 芯片（现有三处多选是 checkbox 列表，形态正确）；异步远程搜索（设备 37、账号 22 全在前端）；虚拟滚动；嵌套分组；inline autocomplete；自由文本模式（一律走"点创建项"，否则"输了一半就失焦"会静默造脏城市——这正是现在 datalist 的病）。
**不替换 `DateTime24` 的时/分 select**：原生 select 的数字 typeahead 和移动端滚轮体验自研做不过浏览器，且它存在的理由是规避 12 小时制渲染，替换收益为负。

**创建项语义（照抄 react-select `useCreatable` 默认值）**
1. normalize 后为空 → 不显示创建项
2. normalize 后**大小写不敏感**地命中任一 option 的 value 或 label → 不显示创建项，改为把那条已有项高亮置顶。**这条是防「上海 / 上海 / 上海」三份分组的核心**
3. `loading === true` → 不显示创建项
4. 点创建项 → 立即调 `onCreate`；异步期间该行显示行内 spinner、菜单保持打开；resolve 后立即选中并关闭；reject 则行内红字、菜单不关、输入保留
5. 乐观更新：返回前先 push 进本地 options，失败回滚
6. **创建后不做二次确认**（四家库都不做）

**键盘与 ARIA（现在一条都没做到）**
- 触发器 `role="combobox"` + `aria-expanded` + `aria-controls` + `aria-haspopup="listbox"`；searchable 时 role 移到 `<input>` 并加 `aria-autocomplete="list"`
- 弹层 `role="listbox"`，选项改成 `<div role="option" aria-selected id={optionId}>`，**不再用 `<button>`**
- **DOM 焦点永远留在触发器/输入框**，高亮靠 `aria-activedescendant`，脚本负责 `scrollIntoView({block:"nearest"})`
- `↓/↑` 开+移动（跳过 disabled）、`Alt+↓` 只开不移、`Home/End`、`PageUp/PageDown` 跳 10、`Enter` 选中、`Esc` 关闭且不改值并把焦点还给触发器、`Tab` 在非搜索形态 = 选中并关闭、非搜索形态支持 typeahead
- 关闭监听补齐：`mousedown` + `keydown(Esc)` + `focusout` + `scroll`(捕获阶段) + `resize`
- 新增全局焦点环 token `--focus-ring`，`:focus-visible` 生效（全站现在 4 条 `:focus`、**0 条 `:focus-visible`**）

**定位：portal，不是 absolute。** 现在 `.filter-dd-menu`（`styles.css:2267`）是 `position:absolute; z-index:20`，**没有 max-height 也没有 overflow-y**。两个已可见的后果：37 台设备的菜单会撑出视口且不可滚；DeviceTasksView 的两个实例在 `.device-tasks-sticky`（`position:sticky; z-index:6`）里，父级建立了新层叠上下文，而 `.app-shell` 还有 `overflow:hidden`（`styles.css:57-63`）。改法：`createPortal(document.body)` + `getBoundingClientRect()` 算位置 + 下方空间不足则上翻 + `max-height:320px; overflow-y:auto`。30 行手写。

### 5.4 FilterBar / PillGroup 规范

```
┌ FilterBar ────────────────────────────────────────────────────────────┐
│ [全部 118] [执行中 3] [需介入 2] [待执行 5] [已完成 613] [失败 75]      │  ← PillGroup（主轴，单选）

│ 已筛选：失败 · 上海 · 今天                                   ✕ 清空    │  ← 摘要行，仅在有非默认筛选时出现
└───────────────────────────────────────────────────────────────────────┘
```

三条规则：主轴用胶囊（基数 ≤6 且是第一眼要看的分类轴），其余进下拉；每个候选值带结果计数；补齐现在缺的"已应用摘要 + 一键清空"。

**PillGroup**：语义 = tabs 单选（`role="tablist"/"tab"`，←→ 键切换）；`count===0` → disabled 灰（防点进空态）；`需介入`/`失败` 在 count>0 时用 `--warn-tint`/`--danger-tint` 着色；上限 6 项。

**收编两个"第三套形态"**：`Overview.tsx:230-237` 的「仅在用账号 · N / 显示全部 · N」裸 toggle 并进 PillGroup；`DeviceTasksView.tsx:203-217` 的「时间 FilterDropdown + `<input type=date>`」并排写同一个 state 互相覆盖 → 改成 Picker 最后一项是「自定义日期…」，点了在菜单内展开 date input。

**状态持久化三件事**
1. **key 集中登记** `frontend/src/lib/filterKeys.ts`（`FK.overviewPlatform` / `FK.deviceTaskDate` / `FK.historyStatus` / `FK.broadcastScope` …）
2. **存语义不存计算值**：时间必须存 `"today"|"yesterday"|"all"|"2026-09-01"`。现在 DeviceTasksView 存的是 `todayStr()` 的结果，一旦持久化，明天打开还停在昨天——这个坑会直接毁掉"默认当天"
3. **介质分两档**：sessionStorage（会话内临时筛选）；localStorage（只给「城市」和「仅在用账号」——运营的长期身份）。localStorage 档加 `window.addEventListener('storage')` 跨标签页同步；顶栏在存在非默认城市筛选时常驻一枚可点即清的标记（如「上海 ✕」）
4. **深链参数只进 state，绝不写持久化**（写进注释，和"不做双向同步"放一起），否则轮询 re-render 会不停改写 URL、污染历史，且会永久篡改运营的默认城市

### 5.5 四个点名问题的改法

**① 群推送没有城市/账号筛选**

两个独立缺口：发送账号是 37 台扁平原生 select（选项 `${昵称}（抖音号 ${id}）` 硬拼、无搜索无分组无占位项、默认吃 `devices[0]`）；群发记录 `records` 硬编码 `t.target_device_id === deviceId`，**只能看当前选中账号的记录**——118 条失败里群发占 68 条散在 37 台机上，现在要一台台切过去看，这才是真正的痛点。

改法：账号选择器换 Picker（searchable + group=城市 + hint=抖音号 + 离线/未登录 disabled）+ 显式占位项；左边加城市 Picker（`worthFiltering` 守卫），切城市时若当前账号不在新城市则清空并 inline 提示，不静默换人；记录区加 FilterBar（PillGroup 全部/成功/失败 + 城市 + **账号范围 Picker「本账号/全部账号」**，默认本账号，持久化）；记录行显示 `error_code ?? current_step` 映射后的原因。

**② 执行记录没有成功/失败筛选**

现状 `HistoryView.tsx:9-12` 只有硬编码白名单 + id 倒序 + 每页 10，零筛选控件，且数据源是被截断到 300 条的全局 tasks。

**必须前后端一起做，且不动 `GET /tasks`**（裁决：原方案的"带参数返回 `{items,total,counts}`、不带参数返回裸数组"是多态响应，会让 `api.ts` 类型定义、每 2 秒的轮询、新分页调用三处同时分叉）：
→ **新开 `GET /tasks/search`，永远返回 `{items, total, counts}`**。参数：`status`(多值)/`device_id`/`platform`/`city`/`publish_type`/`date_from`/`date_to`/`offset`/`limit`。**`counts` 必须是全量 count 查询**，不是当前页统计——否则胶囊上的「失败 75」又变成近似值。同时返回 `by_error_code` 与 `by_current_step` 两套分布（见下）。
→ 前端加 FilterBar + 服务端分页；失败行显示原因短语。

**`failureReason.ts` 从第一天就写成二级映射 `error_code ?? current_step`**，两套 key 共用一张中文短语表。重试方案会把 `confirmation_timeout` 这一个 current_step 拆成 `NORMALIZE_TIMEOUT`/`UNKNOWN_PAGE`/`SECURITY_CHALLENGE` 等多个 error_code；口径不统一，"confirmation_timeout 占比从 84% 降到 <15%"这个头号验收指标就无法被验证。前端分组统计明确标注「口径切换于 YYYY-MM-DD，此前数据仅有 current_step」。

**③ 进设备任务页默认当天**

现状 `DeviceTasksView.tsx:72` 是 `useState("")` = 全部且不持久化。

**改成条件生效，不是无条件默认当天**（裁决：方案要解决的第四个问题恰恰是"找某设备的失败任务"，而失败任务往往是昨天或更早的；无条件默认当天会让它们在默认视图里直接消失，而"空态给看全部按钮"只在当天完全为 0 条时触发）：
- 当天有任务 → 默认当天；顶部胶囊显示 `失败(全部) N` 这种**跨时间维度的计数**，让人知道时间筛选正在隐藏东西
- 当天为空 → 空态里「今天还没有任务」+「看全部」按钮
- **从告警/总览深链进入时一律强制 `date=all&status=failed`**——"点失败告警进来"的意图不是看今天
- 给这条行为加一个 localStorage 开关允许改回"默认全部"，前两周观察实际选择再决定固化
- 存语义值 `"today"` 而非日期串

**④ 找某设备的失败任务要下滑很久 —— 三层原因三层修**

- **层一（真因）：数据被截断。** 全局一条 `limit=300` 喂 37 台机，某台设备的失败任务可能压根不在数组里——**不是滑得久，是找不到**。→ 走 `/tasks/search` 按 `device_id` 单独拉
- **层二（布局）：五个 status group 纵向堆叠**（`DeviceTasksView.tsx:11-17`），「失败/取消」在最后一组。→ 顶部 PillGroup，选中单一状态时不渲染组头，页面从 5 组塌成 1 组
- **层三（入口）：没有深链。** 告警 payload 里带 `device_id` 却不可点（`AlertBell.tsx:114-124` 只渲染文本）；总览卡上的失败数也不可点。→ 两处都加 `onClick` → `?view=device&id={device_id}&status=failed&date=all`，滚动距离 0

**hash 路由归前端方案独家实现**（通知方案不得重复实现）。在 `App.tsx` 加 `useHashRoute()`：解析 `#/<view>[/<id>][?k=v]`，`history.replaceState` 单向同步。支持深链：`#/task/1487`、`#/device/11`、`#/tasks?status=waiting_confirmation&city=上海`、`#/content?city=北京`、`#/ai`、`#/notify`。**未登录时把目标 hash 存进 `sessionStorage.pending_route`，输完 token 后自动跳过去**——这是"点链接 → 输 token → 直接落在 #1487"而不是"落在总览还得自己找"的关键。

**明确不做**：免登录的一次性动作链接（`/alerts/act?t=xxx&op=confirm`）。链接会出现在群聊记录里，等于把"确认已发布/取消任务"的权限泄漏给任何看得到群的人；且 GET 触发副作用会被预览器/爬虫误触发。**便利换不来这个风险**——这是刻意的取舍，不是遗漏。

**只做"看"，不做"操作"。** 运营下班后在手机上只回答一个问题："今天该发的发完了吗，有没有卡住的"。

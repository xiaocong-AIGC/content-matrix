## 这是什么

一套跑在**安卓设备矩阵**上的内容运营 Agent。一个人管几十上百个账号，
从选题、成稿、发布到群内触达，全流程不用人守着。

抖音和小红书都没有开放的内容发布 API。所以 Agent 用**无障碍服务按控件语义**
操作 App —— 不点固定坐标、不刷私有接口。App 挪了个按钮，靠文案和控件树重新找到它，
而不是回去重录一遍坐标。

架构上是 **PC + 设备**分工：设备只负责 App 内的识别与操作，跨 App 的调度由 PC 端做。
单台 PC 可以带一批设备，**规模可扩展到上百台**。

## 内容不是"生成"出来的，是"改编"出来的

这是整个系统最核心的一环。让模型凭空写一篇小红书笔记，你会得到一篇一眼假的 AI 文——
它不知道什么样的封面有人点、什么样的开头有人读完。

所以这里的链路是**数据驱动的二创**：

```
回采真实互动数据 ──► 按互动量筛出被验证的样本 ──► 模型先拆解"为什么它能火"
                                                        │
      成品进内容库 ◄── 确定性机器审核 ◄── 生成 K 条差异化改编 ◄──┘
```

几个关键设计：

- **样本来自真实回采**，含浏览、点赞、收藏、评论；包括那些没匹配上我们发布记录的爆款笔记
  （往往正是表现最好的一批）。
- **模型的任务是"先分析、再改编"**，不是"写一篇"。提示词要求它先提炼样本的胜出结构，
  再产出差异化的新内容。
- **质量决定学谁，城市只决定写哪里。** 低质量地区的本地样本会被全矩阵高分样本顶替 ——
  否则弱势账号会永远学自己一个月前最差的那批，产物再回流样本池，形成自我强化的低水平循环。
- **内容形式可迭代**：系统提示词和参考样本都可以在控制台里换。想从"探店"切到"避坑清单"，
  换一组样本和一段提示词即可，不用改代码。
- **过闸才进库**：地名泄漏用词表确定性拦截，连同字数、时效性表述、封面查重一起作为硬闸 ——
  生成温度高、自动过审时无人过目，靠 prompt 约束的遵守率不可能是 100%，
  而一次地名错配就是对外可见的运营事故。

## 它能做什么

| | 做什么 | 怎么触发 |
|---|---|---|
| **自动生成** | 库存低于设定天数时二创改编出新内容，过审后直接进内容库 | 水位事件驱动 —— 开启城市、内容出池即触发，定时只做兜底 |
| **自动发布** | 到点从内容库取一篇，走完编辑器发出去 | 时间段 + 每号每天篇数；当天失败自动退避重试 |
| **自动群发** | 按排程把消息推进 App 内群聊，支持 @所有人 和配图 | 时间段 + 每天次数，时刻可复现（预览即实际） |
| **矩阵看板** | 账号健康、今日产能、效果榜、执行记录、异常告警 | 实时 |

**多平台**：抖音和小红书共用同一套任务状态机，换一组控件选择器即可。微信在路线图上。

**批量运营**：装机脚本一条命令完成安装、授权、配置、启动，新设备接上就进矩阵。
账号按城市分组，各自独立的发布节奏、内容池和开关。

## 为什么它能放着不管

矩阵运营真正的成本不在"发出去"，在**没人盯着的时候它会怎么样**。
这套东西是照着这个前提做的。

**一台电脑带一批设备。**
安卓系统会拦住后台应用去启动另一个应用——很多自动化方案就卡死在这儿。
这里换了个分法：设备只管 App 里面的事，App 之间的切换交给电脑端。
加设备就是加一个 watcher，不用改任何东西。

**今天没发出去的，今天补上。**
一条发失败，不代表这个号今天就少一篇。系统会把名额还回去，隔一段时间换个时间点再试，
而不是留个红叉等你明天发现。

**最危险的故障，是那种不报错的。**
设备全部在线、一条失败记录都没有、看板上一片绿——但一整天什么都没发出去。
这种情况比报错难发现得多，所以告警不只盯"哪件事失败了"，也盯"该发生的事有没有发生"。

**出了问题，你不用猜。**
每一步都留着截图和日志。是没进到群里，还是压根没打开消息列表——
这两种情况要做的事完全不同，所以我们让它自己说清楚，而不是甩一句"执行失败"。

**App 改版不用重录。**
靠控件语义和文案定位，不靠固定坐标。按钮换个位置、界面调个布局，
它还能找到——这是相比按键精灵那类方案最实在的区别。

## 快速开始

需要 Python 3.11+ / Node 18+ / JDK 17（构建 APK）/ adb。

```bash
# 1. 后端（默认 8010）
cd backend && python -m venv .venv && ./.venv/Scripts/pip install -r requirements.txt
cp .env.example .env          # 填模型 API Key 等
./.venv/Scripts/python run_server.py

# 2. 控制台
cd frontend && npm install && npm run dev

# 3. PC 编排器（每台设备一个 watcher）
python tools/agent_orchestrator.py

# 4. 设备装机（安装 + 授权 + 配置 + 启动，一条命令）
cd android-agent && ./gradlew :app:assembleDebug
python tools/provision_device.py --server http://<你的IP>:8010/api/v1 --serial <设备号> --name 上海01
```

打包分发：

```bash
./build.sh web       # 两份前端：浏览器版（相对路径）+ 桌面版（绝对地址）
./build.sh backend   # 内嵌前端的单体 exe
./build.sh app       # Tauri 桌面壳
```

> 没有设备也能跑通全流程：`agents/simulator/` 是一个 Agent 模拟器。


## 如果你要改代码

几条踩出来的规矩，省得你重踩：

- **控制台 CSS 是自研的**（约 5900 行，无 Tailwind、无组件库），底层有一套设计令牌。
  改样式用 `tools/resolve_css.py` 做**回代 diff**：把所有 `var()` 解开后逐行比对，
  于是"只是改名、页面不动"这句话是机械可证的，不靠比截图。
- **`@media` 按宽度降序**并集中在文件末尾，用 `tools/media_audit.py` 检查 ——
  乱序会让窄断点的规则被宽断点静默盖掉。
- **tsc 通过 + 构建成功不算验证**：下拉、弹窗这类交互的坑只能点出来。
- 后端是**单进程单 worker**：后台循环里做同步 I/O 会按住整个事件循环，
  表现是全站请求一起超时。加循环前先问这一轮有没有网络调用。
